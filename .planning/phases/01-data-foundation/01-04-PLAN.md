Create `src/services/objections.ts` per FRD F02 §Process/§Validation:

```typescript
export async function recordObjection(args: {
  exhibitId: string;
  objectingParty: 'PLAINTIFF' | 'PROSECUTION' | 'DEFENSE';
  grounds: string;
  actorUserId: string;
}): Promise<{ event: ExhibitEvent; objectionState: ObjectionCurrentState }>

export async function recordRuling(args: {
  objectionId: string;
  disposition: 'SUSTAINED' | 'OVERRULED' | 'RESERVED';
  actorUserId: string;
}): Promise<{ event: ExhibitEvent; objectionState: ObjectionCurrentState }>

export async function getUnresolvedObjections(caseId: string): Promise<ObjectionCurrentState[]>
```

`recordObjection` implementation:
1. Validate `grounds` is non-empty.
2. Validate the exhibit's current status (via `prisma.exhibitCurrentState.findUnique`) is `OFFERED` or `OBJECTED` — otherwise throw `INVALID_OBJECTION_TARGET` (422), per F02 §Validation: "cannot object to an exhibit not yet offered, or after it has reached a terminal status."
3. Generate a new `objectionId` (uuid).
4. Call `recordEvent({ exhibitId, eventType: 'OBJECTION_RAISED', payload: { objectionId, objectingParty, grounds }, actorUserId })`.
5. In the same transaction, create an `ObjectionCurrentState` row: `{ objectionId, exhibitId, status: 'UNRESOLVED', objectingParty, grounds, raisedEventId: event.id, raisedAt: event.recordedAt }`.

`recordRuling` implementation:
1. Look up the referenced `objectionId` in `ObjectionCurrentState` — if not found, throw `OBJECTION_NOT_FOUND` (404); if found but `status !== 'UNRESOLVED'`, throw `OBJECTION_ALREADY_RESOLVED` (409).
2. Look up `actorUserId`'s `role` via `prisma.user.findUnique`. **For ALL THREE dispositions — `SUSTAINED`, `OVERRULED`, and `RESERVED` — the role MUST be `JUDGE`.** There is no exception for `RESERVED`: per F02 §Validation, "reserving a ruling is itself a judicial act, not a clerical log entry a deputy/clerk may enter on the judge's behalf." If role is not `JUDGE`, throw `ROLE_NOT_PERMITTED` (403) regardless of which disposition was requested.
3. Call `recordEvent({ exhibitId: objectionState.exhibitId, eventType: 'RULING_RECORDED', payload: { objectionId, disposition }, actorUserId })`.
4. If `disposition` is `SUSTAINED` or `OVERRULED`: update `ObjectionCurrentState.status` to that disposition, set `rulingEventId: event.id`, `ruledAt: event.recordedAt` — thread is now resolved.
5. If `disposition` is `RESERVED`: the ledger event is written (visible in exhibit history/timeline), but `ObjectionCurrentState.status` remains `UNRESOLVED` and `rulingEventId`/`ruledAt` are NOT set — per F02 §Process step 7, a reservation does not close the thread.

`getUnresolvedObjections(caseId)`: `prisma.objectionCurrentState.findMany({ where: { status: 'UNRESOLVED', exhibit: { caseId } } })` — this exact function is the one later called identically by Case Workspace, Command Center, and the assistant (Phase 2/4); no caller-specific variant may exist.

Write `src/services/objections.test.ts`:
- Multi-thread: create two independent objections against the same exhibit (after advancing it to `OFFERED`); assert both appear as separate `UNRESOLVED` rows in `getUnresolvedObjections`.
- Non-judge ruling rejection: attempt `recordRuling` with `disposition: 'RESERVED'` using a `DEPUTY`-role `actorUserId` → rejected with `ROLE_NOT_PERMITTED`. Repeat for `SUSTAINED` and `OVERRULED` with a `CLERK`-role user → both rejected.
- Judge ruling acceptance: `recordRuling` with a `JUDGE`-role user and `disposition: 'RESERVED'` → succeeds, thread remains `UNRESOLVED` in `getUnresolvedObjections`.
- Resolution: `recordRuling` with `disposition: 'SUSTAINED'` by a `JUDGE` → thread no longer appears in `getUnresolvedObjections`.
- Invalid target: `recordObjection` against an exhibit still at `MARKED` status → rejected with `INVALID_OBJECTION_TARGET`.
- Already-resolved: `recordRuling` against an already-`SUSTAINED` objection → rejected with `OBJECTION_ALREADY_RESOLVED`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | `POST /api/objections/:id/ruling` accepts an untrusted `actorUserId` and `disposition` — a malicious or buggy client could attempt to self-assign a ruling without judge role |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-11 | Elevation of privilege | `recordRuling` role enforcement | mitigate | `src/services/objections.ts::recordRuling` step 2 looks up the ACTUAL `role` column for `actorUserId` from the `User` table server-side (never trusts a client-supplied role claim) and rejects any non-JUDGE role for all three dispositions, including RESERVED — this is the single highest-value check in this plan since the FRD explicitly calls out RESERVED as a common mistaken exception |
| T-01-12 | Tampering | `recordRuling` objectionId reference | mitigate | `objectionId` existence + `UNRESOLVED` status is verified server-side against `ObjectionCurrentState` before any ledger write — a client cannot rule on a nonexistent or already-closed thread |
| T-01-13 | Repudiation | Ruling actor attribution | mitigate | Every `RULING_RECORDED` event stores `actorUserId` immutably in the ledger (via `recordEvent`) — the judge who made each ruling is permanently auditable, never overwritable |

</threat_model>
