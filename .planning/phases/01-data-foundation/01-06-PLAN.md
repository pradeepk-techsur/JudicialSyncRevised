<objective>
Build the deterministic seed-data loader (F0a): one `Case`, one `User` per role, a realistic multi-exhibit trial where every status/objection/ruling/custody event is written through the exact same service functions a live UI action would call — with deliberately planted edge cases (unresolved objection, custody gap, jury-package-eligible discrepancy) enforced by a post-seed assertion that fails the entire transaction if any are missing.

Purpose: This is the "zero manual data entry" demonstration requirement and the mechanism that proves the write path is real — if seed data could only be produced by a special direct-DB-insert backdoor, the event-sourcing guarantee would be theater. It must be fully re-runnable from a clean state and produce the same complete case every time.
Output: `src/data/seed.ts`, wired into `npm run seed` and the Docker Compose app boot command (migrate → seed → serve).
</objective>

  <name>Task 1: Seed loader — case, users, exhibits, and planted edge-case histories</name>
  <files>src/data/seed.ts, src/data/seed.test.ts</files>
  <action>
Create `src/data/seed.ts` exporting `async function runSeed(): Promise<{ caseId: string; exhibitCount: number }>`.

**Step 1 — clean-state reset (for deterministic re-runnability):** At the start of `runSeed`, delete all rows in dependency order for any existing seeded case matching a fixed `caseNumber` (e.g. `"2026-CR-0142"`) — delete `ExhibitEvent`, then projection tables (`ExhibitCurrentState`, `ObjectionCurrentState`, `CustodyCurrentState`), then `Exhibit`, then `User`, then `Case` — all scoped to that `caseNumber`. This makes "re-running from a clean state" produce an identical result rather than a duplicate-key error or drifting data.

**Step 2 — identity setup:** Create one `Case` row (`caseNumber: "2026-CR-0142"`, `title`, `court`). Create exactly one `User` per `Role` value (`JUDGE`, `CHAMBERS_STAFF`, `DEPUTY`, `CLERK`, `ATTORNEY`, `ADMIN`) scoped to that case, with deterministic names (e.g. "Judge Elena Marsh", "Deputy Dana Reyes" — drawn from `PERSONAS-JudicialSync.md`/`UserStories-JudicialSync.md` personas for narrative realism).

**Step 3 — exhibit identity records:** Call `createExhibit` (from `src/services/exhibits.ts`, Plan 2) to create 8–10 realistic exhibits (varied `offeringParty`, `description`, `associatedWitness`) — identity fields only, per F00 §Validation.

**Step 4 — plausible histories via the live write path.** For EVERY exhibit, build its history EXCLUSIVELY by calling `recordStatusChange` (Plan 3), `recordObjection`/`recordRuling` (Plan 4), and `recordCustodyTransfer` (Plan 5) — never a direct `prisma.*CurrentState.create`/`prisma.exhibitEvent.create` call. Deliberately include, among the 8-10 exhibits:

- **Exhibit "Unresolved Objection":** advance to `OFFERED`, `recordObjection` against it (any valid `objectingParty`/`grounds`), do NOT record any ruling — thread remains `UNRESOLVED`. (Leave status at `OFFERED` or transition to `OBJECTED` — either is valid per the state machine; advancing to `OBJECTED` is more narratively realistic since an objection exists.)
- **Exhibit "Custody Gap":** advance all the way to `ADMITTED` (`MARKED`→`OFFERED`→`ADMITTED`) with ZERO `recordCustodyTransfer` calls ever made against it — the custody gap is the complete ABSENCE of custody events, not a malformed one.
- **Exhibit "Jury-Eligible Discrepancy":** advance to `ADMITTED` (via `OFFERED`→`OBJECTED`→`ADMITTED`, since `OBJECTED`→`ADMITTED` is an allowed transition even with an open objection, per F1), with `recordObjection` raised and left `UNRESOLVED` (no ruling) — this exhibit is simultaneously `ADMITTED` status AND carries an open objection thread, which is exactly the condition Phase 3's `UNRESOLVED_OBJECTION_JURY_ELIGIBLE` discrepancy rule will detect.
- **4–6 "clean" exhibits:** progress normally through a plausible subset of the lifecycle (some terminal at `ADMITTED` with a full custody chain and no open objections, one `EXCLUDED`, one `WITHDRAWN`) — these exist so the demo doesn't look artificially all-broken, and so Phase 2's screens have non-flagged rows to contrast against the flagged ones.

Use plausible, staggered timestamps implicitly via sequential `recordEvent` calls (each stamps its own `recordedAt: now()` — do not attempt to backdate; relative ordering via `sequenceNo` is what matters for replay determinism, not literal clock times).

**Step 5 — post-seed assertion (fail-fast, not manual review):** After all exhibits are seeded, query:
- `getUnresolvedObjections(caseId)` → length must be ≥ 1
- Exhibits with `currentStatus = 'ADMITTED'` AND no `CustodyCurrentState` row → count must be ≥ 1
- Exhibits with `currentStatus = 'ADMITTED'` AND ≥1 `UNRESOLVED` objection → count must be ≥ 1

If ANY of these three assertions fails, throw a `SeedIntegrityError` (mapped to `SEED_INTEGRITY_FAILURE`, 500) — and because all of Step 2–4's writes happened inside a single outer Prisma `$transaction` (or the reset-and-rebuild is itself wrapped so a thrown assertion error causes the whole seed to roll back), the database is left in its PRE-seed-attempt state, never a partially-loaded one. (If wrapping every `recordEvent` call — each of which opens its own internal transaction — inside one giant outer transaction is impractical with the Prisma client setup from Plan 1, instead perform the post-seed assertion BEFORE declaring success and, on failure, explicitly call the Step 1 cleanup routine again to roll back the partial seed before re-throwing — the net effect of "abort entire seed transaction, never leave partial data" must hold either way.)

Return `{ caseId, exhibitCount }` on success.

Write `src/data/seed.test.ts`:
- Run `runSeed()` once; assert the three edge-case conditions all hold (unresolved objection count ≥1, admitted-no-custody count ≥1, admitted-with-unresolved-objection count ≥1).
- Run `runSeed()` a SECOND time (simulating "re-running from a clean state"); assert the resulting case has the IDENTICAL `exhibitCount` and the same three edge-case conditions still hold (determinism check) — and assert there is still exactly ONE `Case` row with that `caseNumber` (no duplicate accumulation).
- Assert zero direct `prisma.exhibitEvent.create` or `prisma.*CurrentState.create` calls exist in `seed.ts` itself (`grep -c` check in the test, or a static assertion) — the seed must exercise only the Plan 2–5 service functions.
