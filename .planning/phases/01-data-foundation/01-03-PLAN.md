Create `src/services/status.ts` per FRD F01 §Process/§Validation and the Allowed Transitions table:

```typescript
export const ALLOWED_TRANSITIONS: Record<string, ExhibitStatus[]> = {
  NONE: ['MARKED'],       // sentinel for "no prior STATUS_CHANGE event"
  MARKED: ['OFFERED'],
  OFFERED: ['OBJECTED', 'ADMITTED', 'WITHDRAWN'],
  OBJECTED: ['ADMITTED', 'EXCLUDED', 'WITHDRAWN'],
  ADMITTED: [],   // terminal
  EXCLUDED: [],   // terminal
  WITHDRAWN: [],  // terminal
};

export async function recordStatusChange(args: {
  exhibitId: string;
  toStatus: ExhibitStatus;
  actorUserId: string;
  notes?: string;
}): Promise<{ event: ExhibitEvent; currentState: ExhibitCurrentState }>

export async function getExhibitStatus(exhibitId: string): Promise<ExhibitCurrentState | null>
```

Implementation requirements (every rule below maps to a named error in `Y2-errors.md`):
1. Wrap the read-check-write sequence in a Prisma transaction that takes a row lock on the exhibit's current state (use `SELECT ... FOR UPDATE` via `prisma.$queryRaw` against `exhibit_current_state WHERE exhibit_id = $1`, or a Postgres advisory lock keyed by a hash of `exhibitId` when no row exists yet for the exhibit's first-ever transition) — this serializes concurrent status-change requests for the same exhibit so true races cannot produce two valid-looking writes. If the lock cannot be acquired / the transaction fails due to a serialization conflict, catch and re-throw as `STATUS_CONFLICT` (409).
2. Read the exhibit's current status inside that locked transaction: `fromStatus = currentState?.currentStatus ?? 'NONE'`.
3. If `fromStatus` is a terminal status (`ADMITTED`, `EXCLUDED`, `WITHDRAWN`) — i.e. `ALLOWED_TRANSITIONS[fromStatus].length === 0` — throw `STATUS_FINALIZED` (409), regardless of what `toStatus` was requested.
4. If `args.toStatus` is not in `ALLOWED_TRANSITIONS[fromStatus]`, throw `INVALID_STATUS_TRANSITION` (422) with message `"Cannot transition from {fromStatus} to {toStatus}"`.
5. Special case: if `args.toStatus === 'OBJECTED'`, additionally require at least one `ObjectionCurrentState` row for this exhibit with `status = 'UNRESOLVED'` (query `prisma.objectionCurrentState.count({ where: { exhibitId, status: 'UNRESOLVED' } })` — if zero, throw `INVALID_STATUS_TRANSITION` with a message noting no unresolved objection exists).
6. Call `recordEvent({ exhibitId, eventType: 'STATUS_CHANGE', payload: { fromStatus: fromStatus === 'NONE' ? null : fromStatus, toStatus: args.toStatus, notes: args.notes }, actorUserId: args.actorUserId })`.
7. Upsert `ExhibitCurrentState`: `{ exhibitId, currentStatus: args.toStatus, lastStatusEventId: event.id, lastStatusAt: event.recordedAt }` — use `prisma.exhibitCurrentState.upsert` (create on first transition, update thereafter), inside the SAME transaction as the `recordEvent` call so the ledger write and the projection update are atomic (never a window where one exists without the other).
8. `getExhibitStatus` is a plain `prisma.exhibitCurrentState.findUnique({ where: { exhibitId } })` — returns `null` when the exhibit has zero status events (per F00 §Outputs: "an exhibit with zero events ... is reported as 'not yet entered into evidence'").

Write `src/services/status.test.ts`:
- Valid sequence: `MARKED` → `OFFERED` → `ADMITTED`; assert `getExhibitStatus` reflects each step immediately after the corresponding `recordStatusChange` call (read-after-write).
- Invalid transition: fresh exhibit (no events) attempting `toStatus: 'ADMITTED'` directly → rejected with `INVALID_STATUS_TRANSITION`.
- Terminal rejection: exhibit already `ADMITTED` attempting any further `recordStatusChange` → rejected with `STATUS_FINALIZED`.
- `OBJECTED` gating: exhibit at `OFFERED` with zero unresolved objections attempting `toStatus: 'OBJECTED'` → rejected; after creating an `ObjectionCurrentState` row with `status: 'UNRESOLVED'` directly via Prisma fixture, the same transition succeeds.
