Create `src/services/custody.ts` per FRD F03 §Process/§Validation:

```typescript
export async function recordCustodyTransfer(args: {
  exhibitId: string;
  fromCustodianUserId: string | null;
  toCustodianUserId: string;
  reason?: string;
  actorUserId: string;
}): Promise<{ event: ExhibitEvent; custodyState: CustodyCurrentState }>

export async function getCustodian(exhibitId: string): Promise<CustodyCurrentState | null>

export async function getCustodyHistory(exhibitId: string): Promise<Array<{
  fromCustodian: string | null;
  toCustodian: string;
  timestamp: Date;
  reason: string | null;
  eventId: string;
}>>
```

`recordCustodyTransfer` implementation:
1. Read the exhibit's current `CustodyCurrentState` (if any).
2. **Chain validation (the core invalid-action check this feature exists to prove):** `args.fromCustodianUserId` must exactly match the current `currentCustodianUserId` — or both must be absent/null when this is the exhibit's first-ever custody event. If they don't match, throw `CUSTODY_CHAIN_BROKEN` (409): "Recorded custodian does not match the exhibit's current custodian." This is a strict equality check with no fuzzy matching or auto-correction — a transfer "from" the wrong holder is refused outright, never silently reassigned.
3. Validate `toCustodianUserId` references an existing, `isActive: true` user (`prisma.user.findUnique`) — otherwise throw `INVALID_CUSTODIAN` (422).
4. Validate `fromCustodianUserId !== toCustodianUserId` — otherwise throw `NO_OP_TRANSFER` (422): no-op transfers are never valid, even if the chain-of-custody would otherwise "match."
5. Call `recordEvent({ exhibitId, eventType: 'CUSTODY_TRANSFER', payload: { fromCustodianUserId: args.fromCustodianUserId, toCustodianUserId: args.toCustodianUserId, reason: args.reason }, actorUserId: args.actorUserId })`.
6. In the same transaction, upsert `CustodyCurrentState`: `{ exhibitId, currentCustodianUserId: args.toCustodianUserId, since: event.recordedAt, lastEventId: event.id }`.

`getCustodian(exhibitId)`: `prisma.custodyCurrentState.findUnique({ where: { exhibitId } })` — returns `null` when no custody event has ever been recorded (per F03 §Terminology "Custody Gap" — this is a VALID, meaningful state, not an error; the API layer maps this to a clear "no custodian of record" response, never a blank or error).

`getCustodyHistory(exhibitId)`: query all `ExhibitEvent` rows for the exhibit where `eventType = 'CUSTODY_TRANSFER'`, ordered by `sequenceNo` ascending, mapping each row's `payload` to the returned shape (`fromCustodian`/`toCustodian` from `payload.fromCustodianUserId`/`payload.toCustodianUserId`, `timestamp` from `recordedAt`, `reason` from `payload.reason`, `eventId` from `id`). No filtering or truncation — the complete chain, always.

Write `src/services/custody.test.ts`:
- First-ever transfer: `fromCustodianUserId: null` → succeeds, `getCustodian` reflects the new holder immediately.
- Chain-of-custody continuation: second transfer with `fromCustodianUserId` matching the current holder → succeeds.
- **Wrong-holder rejection:** second transfer with `fromCustodianUserId` set to some OTHER user (not the actual current custodian) → rejected with `CUSTODY_CHAIN_BROKEN`, and `getCustodian` is unchanged (still shows the original holder) after the rejected attempt.
- No-op rejection: transfer with `fromCustodianUserId === toCustodianUserId` → rejected with `NO_OP_TRANSFER`.
- Invalid custodian: transfer `toCustodianUserId` referencing a nonexistent user id → rejected with `INVALID_CUSTODIAN`.
- Custody gap: an exhibit with zero custody events → `getCustodian` returns `null` (not an error, not a placeholder row); `getCustodyHistory` returns an empty array.
- Full history: three sequential transfers → `getCustodyHistory` returns exactly 3 entries in chronological order with correct from/to/reason/timestamp for each.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | `POST /api/exhibits/:id/events/custody` accepts untrusted `fromCustodianUserId`/`toCustodianUserId` — a client could attempt to claim a transfer "from" a custodian who doesn't actually currently hold the exhibit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-14 | Tampering | `recordCustodyTransfer` chain validation | mitigate | `src/services/custody.ts::recordCustodyTransfer` step 2 performs a strict server-side equality check between the claimed `fromCustodianUserId` and the actual `CustodyCurrentState.currentCustodianUserId` — a client cannot fabricate a transfer from a custodian who doesn't currently hold the exhibit; rejected with `CUSTODY_CHAIN_BROKEN` before any ledger write |
| T-01-15 | Tampering | `toCustodianUserId` validity | mitigate | Step 3 validates the target user exists and `isActive: true` via a direct `prisma.user.findUnique` lookup — a transfer cannot be recorded to a nonexistent or deactivated user id |
| T-01-16 | Repudiation | Custody transfer actor attribution | mitigate | Every `CUSTODY_TRANSFER` event immutably records `actorUserId` (who logged the transfer) distinct from `fromCustodianUserId`/`toCustodianUserId` (who physically held it) via `recordEvent` — supports the FRD's "a clerk logging on behalf of a deputy" scenario while preserving full audit attribution |

</threat_model>
