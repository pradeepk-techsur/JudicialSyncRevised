```typescript
import { z } from 'zod';

export const offeringPartyEnum = z.enum(['PLAINTIFF', 'PROSECUTION', 'DEFENSE']);
export const exhibitStatusEnum = z.enum(['MARKED', 'OFFERED', 'OBJECTED', 'ADMITTED', 'EXCLUDED', 'WITHDRAWN']);

export const statusChangePayload = z.object({
  fromStatus: exhibitStatusEnum.nullable(),
  toStatus: exhibitStatusEnum,
  notes: z.string().optional(),
});

export const objectionRaisedPayload = z.object({
  objectionId: z.string().uuid(),
  objectingParty: offeringPartyEnum,
  grounds: z.string().min(1),
});

export const rulingRecordedPayload = z.object({
  objectionId: z.string().uuid(),
  disposition: z.enum(['SUSTAINED', 'OVERRULED', 'RESERVED']),
});

export const custodyTransferPayload = z.object({
  fromCustodianUserId: z.string().uuid().nullable(),
  toCustodianUserId: z.string().uuid(),
  reason: z.string().max(300).optional(),
});

export const discrepancyAcknowledgedPayload = z.object({
  discrepancyFlagId: z.string().uuid(),
  ruleCode: z.string(),
  justification: z.string().min(1).max(500),
});

export const eventPayloadSchemas = {
  STATUS_CHANGE: statusChangePayload,
  OBJECTION_RAISED: objectionRaisedPayload,
  RULING_RECORDED: rulingRecordedPayload,
  CUSTODY_TRANSFER: custodyTransferPayload,
  DISCREPANCY_ACKNOWLEDGED: discrepancyAcknowledgedPayload,
} as const;
```
(`DISCREPANCY_ACKNOWLEDGED`'s schema is included for completeness per Y0-schema.md's full payload table even though no Phase 1 caller emits it yet — Phase 3 will.)

Create `src/services/events.ts` with `recordEvent`:
```typescript
export async function recordEvent(args: {
  exhibitId: string;
  eventType: EventType;
  payload: unknown;
  actorUserId: string;
}): Promise<ExhibitEvent>
```
Implementation requirements:
- Validate `args.payload` against `eventPayloadSchemas[args.eventType]` (zod `.parse` — throw a typed `ValidationError` on failure, caught by API routes as 422 `VALIDATION_ERROR`).
- Inside a single Prisma `$transaction`: compute `sequenceNo` as `(max existing sequenceNo for this exhibitId) + 1` (use `prisma.exhibitEvent.aggregate({ where: { exhibitId }, _max: { sequenceNo: true } })`, default 1 when none exist), then `prisma.exhibitEvent.create(...)` with that `sequenceNo` and `recordedAt: new Date()`.
- This is the ONLY function in the codebase permitted to call `prisma.exhibitEvent.create`. Every later plan (status, objections, custody) calls `recordEvent`, never Prisma directly for ledger writes.
- Return the full created `ExhibitEvent` row (including `id`, for citation use by later features).

Write `src/services/events.test.ts` (vitest, against the real Postgres from `docker-compose.yml`): seed a minimal `Case`/`User`/`Exhibit` via Prisma directly (test fixture only — not via `recordEvent`, since there's no status yet), then:
- Call `recordEvent` twice for the same exhibit with `STATUS_CHANGE` payloads; assert `sequenceNo` increments 1, 2 and both rows are immediately queryable via `prisma.exhibitEvent.findMany`.
- Call `recordEvent` with an invalid payload (missing required field); assert it throws/rejects before any row is inserted (query count unchanged).

```typescript
export async function createExhibit(input: {

```
Validation (per F00 §Validation, enforced before the Prisma call):
- `description` max 1000 chars (also DB-enforced via the CHECK constraint from TechArch §3.2, but validate at the service layer first for a clean 422 instead of a raw Postgres constraint error).
- `offeringParty` must be one of the three enum values (zod).
- On a unique-constraint violation for `(caseId, exhibitLabel)` (Prisma error code `P2002`), catch and re-throw a typed `ConflictError` with code `EXHIBIT_LABEL_CONFLICT` — do NOT let the raw Prisma error leak to the API layer.
- `createExhibit` accepts ONLY identity fields — there is no `status`/`custody` parameter in its signature at all (not merely unused; structurally absent), per F00 §Validation: "An Exhibit cannot be created with any status/custody field directly."

Note (deliberate, documented scope decision): role-based visibility filtering (sealed-exhibit exclusion per `00-header.md` §Role-Based Visibility) is NOT implemented in `getExhibit`/`getExhibits` in this phase — it is deferred to Phase 2, where the first UI/API consumer actually needs `requestingUserRole` plumbed through. The `isSealed` field is stored faithfully now; filtering logic is added when a real caller needs it, avoiding speculative plumbing ahead of its consumer.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | `POST /api/exhibits` and the GET routes accept untrusted request bodies/path params (`caseId`, `exhibitLabel`, `offeringParty`, etc.) |
| db→render | Exhibit `description`/`source`/`associatedWitness` free-text fields are later rendered in UI screens (Phase 2) — not sanitized here, but no raw HTML/script execution risk since Next.js/React escapes by default |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Tampering | `POST /api/exhibits` body parsing | mitigate | All fields validated via zod in `createExhibit` (Task 2) before any Prisma call; `offeringParty` constrained to the exact 3-value enum, `description` length-capped — no raw/unvalidated input reaches a Prisma write |
| T-01-05 | Tampering | `recordEvent` payload | mitigate | `eventPayloadSchemas` discriminated-union validation in `src/services/events.ts` rejects any payload shape not matching the declared `eventType` before the transaction opens — malformed ledger rows are structurally impossible |
| T-01-06 | Elevation of privilege | `createExhibit` input surface | mitigate | Function signature structurally excludes any status/custody parameter (Task 2) — there is no code path, not even a malicious caller, that can set initial status/custody via exhibit creation |
| T-01-07 | Information disclosure | `GET /api/exhibits/:id` on sealed exhibits | accept | Role-based visibility (sealed-exhibit masking as 404) is explicitly deferred to Phase 2 per this plan's scope decision (Task 2) — owner: Phase 2 planner, tracked via FRD F10 §Validation; residual risk is limited to this phase having no UI/multi-role consumer yet, so no real exposure exists until Phase 2 introduces role-scoped screens |
