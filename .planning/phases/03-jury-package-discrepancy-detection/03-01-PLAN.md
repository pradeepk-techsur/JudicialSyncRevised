  <name>Task 2: Build the discrepancy rule engine + error codes</name>
  <files>src/lib/errors.ts, src/services/discrepancies.ts, src/services/discrepancies.test.ts</files>
  <action>
Add a reusable `RoleNotPermittedError` to src/lib/errors.ts (403, code `ROLE_NOT_PERMITTED`, default message "You are not permitted to perform this action" with an optional override) — objections.ts already has a private one for ruling; this shared class is for the discrepancy/jury features. Do NOT remove objections.ts's existing private class in this task.

Create `src/services/discrepancies.ts`. It reads the PROJECTIONS only (exhibit_current_state, objection_current_state, custody_current_state) — NEVER scans exhibit_events (TechArch §3.8). Export:

1. `RULE_CODES` constant / rule registry (two rules, from TechArch):
   - `ADMITTED_NO_CUSTODIAN` — fires when ExhibitCurrentState.currentStatus = 'ADMITTED' AND no CustodyCurrentState row exists for the exhibit.
   - `UNRESOLVED_OBJECTION_JURY_ELIGIBLE` — fires when ExhibitCurrentState.currentStatus = 'ADMITTED' AND ≥1 ObjectionCurrentState row for the exhibit has status = 'UNRESOLVED'.

2. `evaluateDiscrepancies(exhibitId: string, client?: PrismaClient | Prisma.TransactionClient): Promise<void>` — accepts an optional tx client (same PrismaLike pattern as recordEvent) so callers run it INSIDE their existing transaction. Algorithm (FRD F06 process + Y3 internal triggers):
   a. Load the exhibit's caseId, its ExhibitCurrentState, its CustodyCurrentState (presence/absence), and its UNRESOLVED ObjectionCurrentState count — all via the passed client.
   b. For each rule: compute `fires` (boolean) from the projections.
   c. Load existing DiscrepancyFlag rows for this (exhibitId, ruleCode).
   d. If `fires` AND there is NO existing OPEN or ACKNOWLEDGED flag for that exhibit+rule → create a new flag (status OPEN, detectedAt now, details = a JSON object describing the mismatch, e.g. `{ currentStatus, hasCustody:false }` or `{ currentStatus, unresolvedObjectionCount }`).
   e. If NOT `fires` → for every existing OPEN or ACKNOWLEDGED flag for that exhibit+rule, set status RESOLVED, resolvedAt now. (resolvedByEventId is set by the triggering caller when it has the event id; evaluateDiscrepancies itself may leave it null — see note below.) Use `updateMany` keyed on exhibitId+ruleCode+status in [OPEN, ACKNOWLEDGED].
   f. Never create a duplicate OPEN flag when one already exists (idempotent re-evaluation is safe to call on every write).

   resolvedByEventId handling: evaluateDiscrepancies takes an optional `resolvingEventId?: string` arg so the triggering write (status/ruling/custody) can attribute the resolution to the event it just recorded. When absent, leave resolvedByEventId null. detectedAt/resolvedAt use `new Date()`.

3. `getDiscrepancies(caseId: string): Promise<DiscrepancyFlag[]>` — all flags case-wide with status in (OPEN, ACKNOWLEDGED), ordered detectedAt asc. RESOLVED flags are excluded (they are history, surfaced only in the timeline). This is the shared query for F9/F11/Command Center.

4. `getExhibitDiscrepancies(exhibitId: string): Promise<DiscrepancyFlag[]>` — same but scoped to one exhibit.

5. `acknowledgeDiscrepancy(args: { discrepancyFlagId: string; actorUserId: string; justification: string }): Promise<{ event: ExhibitEvent; discrepancyFlag: DiscrepancyFlag }>`:
   - Trim justification; if empty → throw `new UnprocessableError('JUSTIFICATION_REQUIRED', 'A justification is required to acknowledge a discrepancy')`.
   - Load the flag; if missing → throw `new NotFoundError('DISCREPANCY_NOT_FOUND', 'No discrepancy found with the given ID')`.
   - Role gate: resolve actorUserId's User.role; must be one of DEPUTY/CLERK/JUDGE/ADMIN (F6) else throw the shared `RoleNotPermittedError`.
   - IDEMPOTENT: if the flag is already ACKNOWLEDGED or RESOLVED, return the existing flag + its existing acknowledgedEvent (look it up; if RESOLVED with no ack event, return a representative — simplest: re-read and return current state with the most recent DISCREPANCY_ACKNOWLEDGED event for that flag if any). Do NOT write a second ledger event. The route maps this to 200.
   - Otherwise (status OPEN): in ONE `prisma.$transaction`, call `recordEvent({ exhibitId: flag.exhibitId, eventType: 'DISCREPANCY_ACKNOWLEDGED', payload: { discrepancyFlagId, ruleCode: flag.ruleCode, justification }, actorUserId }, tx)` — the payload is already validated by the existing discrepancyAcknowledgedPayload zod schema — then `tx.discrepancyFlag.update` setting status ACKNOWLEDGED, acknowledgedAt now, acknowledgedBy actorUserId, acknowledgedEventId = event.id. Return { event, discrepancyFlag }. The ledger event + flag update MUST commit together (TechArch §3.8 — they must never diverge).

Follow the existing service style: typed errors from @/lib/errors, recordEvent as the sole ledger writer, the validate→recordEvent(tx)→projection-write transaction template.

Create `src/services/discrepancies.test.ts` (vitest integration, against the shared Postgres; this is the backend integration-test requirement for new services). Because fileParallelism:false and suites share the fixed-caseNumber seed, build a SELF-CONTAINED minimal fixture case with a unique caseNumber (e.g. `TEST-DISC-<random>`) created+torn down in beforeAll/afterAll via the service write paths, OR drive it off a freshly-seeded case — follow whichever the existing history.test.ts / custody.test.ts do. Cover:
  - ADMITTED exhibit with no custody → evaluateDiscrepancies creates exactly one OPEN ADMITTED_NO_CUSTODIAN flag; calling again does NOT create a second.
  - Recording a custody transfer then re-evaluating → the flag becomes RESOLVED.
  - ADMITTED exhibit with an UNRESOLVED objection → one OPEN UNRESOLVED_OBJECTION_JURY_ELIGIBLE flag; ruling SUSTAINED/OVERRULED + re-evaluate → RESOLVED.
  - acknowledgeDiscrepancy by a DEPUTY: writes a DISCREPANCY_ACKNOWLEDGED event and flips the flag to ACKNOWLEDGED (assert both, same call).
  - acknowledgeDiscrepancy with empty/whitespace justification → throws JUSTIFICATION_REQUIRED (422).
  - acknowledgeDiscrepancy by an ATTORNEY → throws ROLE_NOT_PERMITTED (403).
  - acknowledgeDiscrepancy on an already-ACKNOWLEDGED flag → idempotent, no second ledger event (assert the DISCREPANCY_ACKNOWLEDGED event count for that exhibit stays 1).

| Boundary | Description |
|----------|-------------|
| client→API (service inputs) | acknowledgeDiscrepancy receives actorUserId + justification originating from a request body; the engine runs inside privileged write transactions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Elevation of privilege | acknowledgeDiscrepancy role gate | mitigate | Resolve actorUserId's actual User.role server-side (prisma.user.findUnique) and reject any role outside DEPUTY/CLERK/JUDGE/ADMIN via RoleNotPermittedError in src/services/discrepancies.ts — never trust a client-supplied role claim (mirrors objections.ts recordRuling T-01-11). |
| T-03-02 | Tampering | DISCREPANCY_ACKNOWLEDGED payload | mitigate | Payload validated by the existing discrepancyAcknowledgedPayload zod schema inside recordEvent before the row is written; justification min(1).max(500) enforced there and re-checked (trim) in acknowledgeDiscrepancy for the JUSTIFICATION_REQUIRED 422. |
| T-03-03 | Repudiation | silent discrepancy dismissal | mitigate | Acknowledgment can ONLY move OPEN→ACKNOWLEDGED by appending an immutable DISCREPANCY_ACKNOWLEDGED ledger event in the same transaction as the flag update (src/services/discrepancies.ts acknowledgeDiscrepancy) — there is no code path that mutates flag.status to ACKNOWLEDGED without a corresponding ledger row. |
| T-03-04 | Tampering | ledger-write chokepoint | mitigate | discrepancies.ts writes the ledger exclusively through recordEvent(args, tx); grep in Task 2 verify asserts zero direct exhibitEvent.create call sites, preserving the single-writer invariant. |
