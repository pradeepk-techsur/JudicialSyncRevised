Create `src/services/juryPackage.ts`. Follow the established service style (typed errors, projection reads, recordEvent as sole ledger writer where a ledger write is needed). Role authorization for writes resolves actorUserId's actual User.role; sealed-visibility for the RETURNED VIEW uses the passed requestingUserRole + canViewSealed (import from @/services/visibility). Import `DiscrepancyFlagSummary` from `@/lib/types` and `ruleLabel` from `@/lib/discrepancyLabels` (both provided by 03-01 in wave 1 — do NOT redefine them).

Define and EXPORT a `JuryPackageExhibitView` interface. It extends the TechArch 03-api.md shape with ONE additive field (`flags`) — note this divergence in 03-02's SUMMARY:
```typescript
export interface JuryPackageExhibitView {
  exhibitId: string;
  exhibitLabel: string;
  currentStatus: ExhibitStatus;   // ADMITTED for all rows
  discrepancyStatus: 'CLEAN' | 'FLAGGED';  // LIVE, freshly evaluated — kept for backward-compat with TechArch; collapses OPEN+ACKNOWLEDGED
  flags: DiscrepancyFlagSummary[]; // ADDITIVE: per-flag OPEN/ACKNOWLEDGED summaries so the client can (a) style each flag and (b) compute "any OPEN remaining" for the hard-disabled gate. Empty [] when CLEAN.
  addedAt: string;
}
```
Why the additive field (BLOCKER fix): `discrepancyStatus: CLEAN|FLAGGED` collapses OPEN and ACKNOWLEDGED, but 03-04's hard-disabled finalize gate must block ONLY on OPEN and RE-ENABLE once all flags are acknowledged. From `FLAGGED` alone the client cannot distinguish "acknowledged → enable finalize" from "open → keep disabled". `flags[]` carries exactly enough (each `{ ruleCode, status: OPEN|ACKNOWLEDGED, label }`) for both the per-flag badge styling AND the `flags.some(f => f.status === 'OPEN')` gate computation. This is delivered HERE in 03-02 (not deferred to 03-04) so the GET/POST route contracts and their tests are right from wave 2 — 03-04 purely consumes it.

SEALED-MEMBERSHIP POLICY (WARNING-3 fix — read before implementing the three functions below). Jury-package MEMBERSHIP (which JuryPackageExhibit rows persist) is CASE TRUTH and MUST be viewer-independent: it is computed with a FIXED FULL-visibility role, NEVER the acting user's role. Sealed exhibits are filtered ONLY when SHAPING the returned view/export list, per the requesting role. This is mandatory because:
  - If a DEPUTY (not in SEALED_VISIBLE_ROLES — confirmed in src/services/visibility.ts) initiated or reconciled a package using their own role, sealed admitted exhibits would be EXCLUDED from membership, while an ADMIN touching the same draft would reconcile them IN — making persisted membership depend on who last touched it.
  - Worse, a sealed exhibit with an OPEN discrepancy could then be absent from membership and finalize could quietly succeed with that discrepancy unresolved — a silent breach of ROADMAP criterion 3 "any included exhibit".
So: membership computation = full visibility; the finalize gate reads MEMBERSHIP (all JuryPackageExhibit rows, including sealed), not the role-filtered view; the returned view/export is the ONLY place canViewSealed filtering is applied. This matches "Sealed-Exhibit Invisibility applies to the view/export", not to membership.

1. `computeJuryCandidates(caseId: string, requestingUserRole: Role): Promise<{ exhibitId: string; exhibitLabel: string; currentStatus: 'ADMITTED'; isSealed: boolean }[]>`
   - Read ExhibitCurrentState WHERE currentStatus = 'ADMITTED' joined to exhibits of this case — with NO sealed exclusion in the WHERE. Return ALL admitted exhibits (membership is full-visibility), each carrying its `isSealed` flag so callers can role-filter the returned VIEW. Order by exhibitLabel asc.
   - The `requestingUserRole` param is retained for the VIEW-shaping callers use (they drop `isSealed && !canViewSealed(requestingUserRole)` rows from the returned list), but it MUST NOT change which rows are considered members/candidates.

2. `initiateJuryPackage(caseId: string, actorUserId: string, requestingUserRole: Role): Promise<{ juryPackage: JuryPackage; exhibits: JuryPackageExhibitView[] }>` — the EXPLICIT initiate (POST).
   - Role gate: actorUserId's role must be DEPUTY/CLERK/ADMIN else RoleNotPermittedError (403).
   - One-living-DRAFT, idempotent: if a DRAFT JuryPackage already exists for the case, do NOT create a second — reconcile it (see getJuryPackage reconcile logic) and return it. If the most recent package is FINALIZED, create a NEW DRAFT from current candidates.
   - MEMBERSHIP candidates = computeJuryCandidates(caseId, requestingUserRole) read for membership = ALL admitted exhibits (the function no longer excludes sealed). Persist a JuryPackageExhibit row for EVERY admitted exhibit regardless of the actor's sealed visibility — membership is case truth. Then shape the RETURNED view by dropping rows that are `isSealed && !canViewSealed(requestingUserRole)`.
   - If zero MEMBERSHIP candidates (no admitted exhibits at all) → throw `new UnprocessableError('NO_ELIGIBLE_EXHIBITS', 'No admitted exhibits are eligible for a jury package')` (422). (Base this on membership, not the role-filtered view, so the 422 reflects true eligibility.)
   - Create the JuryPackage (status DRAFT) and its JuryPackageExhibit rows for all members (discrepancyStatus = live CLEAN/FLAGGED per exhibit — see mapping below) in one transaction. Return the role-filtered view.

3. `getJuryPackage(caseId: string, requestingUserRole: Role): Promise<{ juryPackage: JuryPackage | null; exhibits: JuryPackageExhibitView[] }>` — READ-ONLY (ROADMAP criterion 5 + F11). MUST NOT create a package as a side effect.
   - SUPERSESSION NOTE (WARNING-2, record in SUMMARY): ROADMAP criterion 5 ("never create on view") SUPERSEDES both CONTEXT line 23's "...returns the existing DRAFT or creates one" wording AND Y1-api's non-nullable GET response type. GET is strictly read-only: it returns `juryPackage: null` when none exists (never creating one), and reconcile-only (never create) on an existing DRAFT. Do NOT "fix" GET to create-on-view — that would break criterion 5. This is a deliberate spec reconciliation, not an oversight.
   - Find the most recent JuryPackage for the case (order createdAt desc).
   - If NONE → return `{ juryPackage: null, exhibits: [] }` (the "no package started yet" state). Create nothing.
   - If FINALIZED → return it read-only with its stored JuryPackageExhibit rows mapped to the view (finalized snapshot; shape the RETURNED list by dropping `isSealed && !canViewSealed(requestingUserRole)` rows — the persisted membership is untouched).
   - If DRAFT → RECONCILE membership to the live ADMITTED set (CONTEXT "Auto-reconcile"): compute current candidates via computeJuryCandidates (FULL-visibility membership — NOT scoped to requestingUserRole), add JuryPackageExhibit rows for newly-admitted exhibits, remove rows for exhibits no longer ADMITTED. Membership reconcile is viewer-independent (per the policy above) so the persisted rows never depend on who loaded the draft. This reconcile MAY write (add/remove rows + refresh the stored discrepancyStatus hint) — a legitimate reconcile, distinct from "creating a draft on view". The prohibition is specifically on CREATING a package when none exists; reconciling an EXISTING draft is explicitly allowed by CONTEXT. Then return the role-filtered live view (drop sealed rows the requesting role can't see).

   Live discrepancy mapping (used by all three above — produces each row's `discrepancyStatus` AND `flags[]`): for each member/candidate exhibit, call `getExhibitDiscrepancies(exhibitId)` (returns OPEN+ACKNOWLEDGED flags). Map each flag to a `DiscrepancyFlagSummary` `{ ruleCode, status, label: ruleLabel(ruleCode) }` → that array is the row's `flags`. Set `discrepancyStatus = flags.length > 0 ? 'FLAGGED' : 'CLEAN'` (kept for backward-compat). The stored `discrepancy_status` column is refreshed to this CLEAN/FLAGGED value on reconcile so it never silently diverges, but the VIEW always reflects the fresh computation — and `flags[]` is ALWAYS freshly computed, never read from the stored column. (The finalize GATE does NOT use the view's `discrepancyStatus` OR `flags` — it re-evaluates over membership directly; see finalize below.)

4. `finalizeJuryPackage(juryPackageId: string, actorUserId: string, acknowledgedDiscrepancyIds?: string[]): Promise<{ juryPackage: JuryPackage }>` — hard gate, re-evaluated FRESH.
   - Load the package; if missing → NotFoundError('JURY_PACKAGE_NOT_FOUND', ...) 404.
   - If already FINALIZED → throw `new ConflictError('JURY_PACKAGE_ALREADY_FINALIZED', 'This jury package has already been finalized')` 409.
   - Role gate: actorUserId role must be DEPUTY/CLERK/ADMIN else RoleNotPermittedError 403.
   - FRESH re-evaluation over MEMBERSHIP: the gate reads ALL JuryPackageExhibit rows of the package (membership — INCLUDING sealed exhibits the acting user cannot see), NOT any role-filtered view. For EVERY member JuryPackageExhibit, call `evaluateDiscrepancies(exhibitId)` (no tx — fresh standalone eval, OR inside the finalize transaction for atomicity; prefer inside the transaction) so flags reflect current state, then read each exhibit's flags. An exhibit BLOCKS iff it has ≥1 flag with status OPEN. ACKNOWLEDGED and RESOLVED do NOT block. NEVER trust the cached JuryPackageExhibit.discrepancyStatus column for the gate. (Because membership is full-visibility, a sealed exhibit with an OPEN discrepancy correctly blocks finalize even for a deputy who never saw it on screen — WARNING-3 honesty.)
   - If any blocking exhibits → throw `new ConflictError('JURY_PACKAGE_DISCREPANCIES_OPEN', \`Cannot finalize: ${n} exhibit(s) have unresolved discrepancies\`, { blockingExhibits })` — passing the blocking list as the OPTIONAL `details` arg that 03-01 added to AppError/ConflictError. `blockingExhibits` = `{ exhibitId, exhibitLabel, ruleCodes: string[] }[]` for every member exhibit with ≥1 OPEN flag. The 409 body MUST name the blocking exhibit(s) (ROADMAP criterion 3); errorResponse (already extended in 03-01 to surface `details`) emits them as `{ error: { code, message, details: { blockingExhibits } } }`. Do NOT add the `details` plumbing here — it is provided by 03-01; this task CONSUMES it. (Note: the blocking list may include sealed exhibits the acting user can't normally see; this is acceptable — the acting role is a privileged DEPUTY/CLERK/ADMIN finalizer and naming the blocker by label is required to unblock; the label is already minimal metadata, not the sealed content. If stricter sealed-label redaction is later required it is a follow-up, not this phase.)
   - If clean → update JuryPackage to status FINALIZED, finalizedAt now, finalizedBy actorUserId. Return it.

Error-envelope note: the `details` channel is already wired in 03-01 (optional `details?` on AppError + subclasses, surfaced by errorResponse as `{ error: { code, message, details? } }`, omitted when undefined). This task only PASSES `{ blockingExhibits }` as the ConflictError `details` arg — it does NOT modify src/lib/errors.ts or src/lib/apiError.ts (those are owned by 03-01).
