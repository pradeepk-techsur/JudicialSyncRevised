Purpose: A user clicking anywhere on an exhibit row except its exact wired hit-area gets no response (a usability regression); a user tapping an example prompt gets a confident-sounding but fabricated-reference question that can never resolve to a real record.
Output: Every pixel of every Case Workspace row is clickable and keyboard-activatable; every assistant example prompt references a real, currently-seeded exhibit label.
</objective>

Nested inline action controls call `stopPropagation()` so operating them never triggers row navigation, while every other point on the row does." The Command Center's Recent Activity/Unresolved Objections/Discrepancies rows are cited as the ALREADY-CORRECT reference implementation — if useful, inspect `src/components/command-center/RecentActivityPanel.tsx`'s row markup for a working pattern to mirror (it currently uses a `<Link>` wrapper rather than a `<TableRow onClick>`, so the mechanism will differ, but the keyboard/hover-affordance CONTRACT is the same).

**Current state (already confirmed in this planning session):** `ExhibitTable.tsx`'s `<TableRow>` already has `onClick={() => router.push(...)}` and `className={styles.row}` (which already sets `cursor: pointer`) — yet the bug report says rows are not reliably clickable. Likely candidates per the FRD: Carbon's `TableRow` swallowing the click via an internal handler, a nested interactive element (the `DiscrepancyBadge`'s `Tag` component, or `StatusBadge`) eating the click before it bubbles, a CSS pointer-events issue on a child element, or the row's hit-area not covering its full visual bounds (e.g. padding/margin not included in the clickable box). Diagnose this directly against the running dev server — do not guess blind.

  await page.goto('/case');
  const row = page.locator('[data-testid="exhibit-row"][data-exhibit-label="P-4"]');

  if (!box) throw new Error('row has no bounding box');
  // Click near the far-left edge (Label cell) and far-right edge (last cell)
