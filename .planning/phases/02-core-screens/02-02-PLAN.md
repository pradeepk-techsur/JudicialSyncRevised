Create `src/services/visibility.ts` — the single shared authorization module (`00-header.md` §Role-Based Visibility, `04-security.md` §5.2.1):

```typescript
import type { Role } from '@prisma/client';
import type { NextRequest } from 'next/server';

// Role-Based Visibility (FRD 00-header.md; TechArch 04-security.md §5.2.1).
// Sealed-exhibit exclusion is applied as a WHERE predicate inside every
// service-layer read function that returns exhibit rows — never as a
// post-query filter in a route or UI component. This module is the single
// place that table lives, so it can never drift between getExhibit,
// getExhibits, searchExhibits, and getExhibitHistory.

const SEALED_VISIBLE_ROLES: ReadonlySet<Role> = new Set(['JUDGE', 'CHAMBERS_STAFF', 'ADMIN']);
const ALL_ROLES: ReadonlySet<string> = new Set([
  'JUDGE',
  'CHAMBERS_STAFF',
  'DEPUTY',
  'CLERK',
  'ATTORNEY',
  'ADMIN',
]);

export function canViewSealed(role: Role): boolean {
  return SEALED_VISIBLE_ROLES.has(role);
}

// There is no session/auth layer (PROJECT.md scope) — the demo's role switcher
// sends its active role as a plain `X-User-Role` request header (TechArch
// §4.12 RequestContext). A missing or invalid header fails CLOSED to the
// least-privileged role (ATTORNEY: no sealed visibility) rather than throwing
// or defaulting to full visibility — there is nothing to authenticate against,
// so "unrecognized" must never be treated as "trusted."
export function parseRequestingRole(request: NextRequest): Role {
  const header = request.headers.get('x-user-role');
  if (header && ALL_ROLES.has(header)) {
    return header as Role;
  }
  return 'ATTORNEY';
}
```

Update `src/services/exhibits.ts`'s `getExhibit` to accept and apply the role:
```typescript
export async function getExhibit(exhibitId: string, requestingUserRole: Role): Promise<Exhibit | null> {
  return prisma.exhibit.findFirst({
    where: {
      id: exhibitId,
      ...(canViewSealed(requestingUserRole) ? {} : { isSealed: false }),
    },
  });
}
```
(Switched from `findUnique` to `findFirst` because `findUnique`'s `where` is restricted to unique-indexed fields only — adding the `isSealed` predicate alongside `id` requires `findFirst`; `id` remains the primary key so this is not a performance regression.)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | `X-User-Role` is a plain, unauthenticated client-supplied header (no session/JWT exists) — it governs READ visibility only, never write authorization, consistent with the demo's explicitly no-production-auth scope |
| db→render | Sealed-exhibit existence must not leak through timing, response size, or error-message differences between the "sealed+unauthorized" and "genuinely missing" cases |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Information disclosure | `GET /api/exhibits/:id`, `GET /api/exhibits/:id/history` | mitigate | `getExhibit` applies `isSealed: false` as a `findFirst` WHERE predicate (`src/services/exhibits.ts`) whenever `canViewSealed(role)` is false — the row is never fetched, so there is no later code path that could accidentally render partial sealed content; `getExhibitHistory` inherits this by calling `getExhibit` first and returning `null` immediately, never reaching the event-ledger query |
| T-02-04 | Spoofing | `X-User-Role` header trust | accept | No cryptographic verification of the header is possible (no auth layer exists) — explicitly accepted per `04-security.md` §5.1 "Authentication (Demo-Scoped)"; the residual risk (any client can claim any role) is a documented, scoped product decision, not a lapsed mitigation | Product (TechArch §5.1) |
| T-02-05 | Information disclosure | Anti-enumeration — distinguishing sealed-unauthorized from genuinely-missing | mitigate | Both routes throw the identical `NotFoundError('EXHIBIT_NOT_FOUND', 'No exhibit found with the given ID')` for both cases — verified by a deep-equal response-body assertion in each route's test file (Task 1, Task 2), not just a matching HTTP status code |
| T-02-06 | Elevation of privilege | Default role when `X-User-Role` is missing/malformed | mitigate | `parseRequestingRole` fails closed to `'ATTORNEY'` (the least-privileged role w.r.t. sealed visibility) rather than throwing or defaulting to a privileged role — `src/services/visibility.ts` |
