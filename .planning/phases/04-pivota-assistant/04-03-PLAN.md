<objective>
Build the server endpoints that turn the tool layer into a working assistant: the streaming `POST /api/assistant/chat` route (AI SDK streamText at temperature 0 against Anthropic, with the 8-tool set and the cite-or-decline prompt), the conversation/message/citation persistence service, and the `GET /api/assistant/conversations/:id` replay endpoint. Purpose: This is where the five named demo questions actually resolve, where every factual claim gets a persisted citation, and where the hard line between a Decline (model text) and an error (503 channel) is drawn — the three visually-unambiguous outcomes depend on this backend separation.

Output: `src/services/assistant.ts`, `POST /api/assistant/chat`, `GET /api/assistant/conversations/:id`, and integration tests proving the 5 questions resolve, zero-ungrounded, sealed→decline, 503-on-missing-key, and error-never-rendered-as-decline.

Accept the useChat message array AND the tagging fields (caseId/userId/conversationId/role threaded via useChat `body`/headers — 04-04 wires the client side; here, read role from `parseRequestingRole(request)` as every other route does, and read caseId/userId/conversationId from the request body or custom headers). 3. **Conversation:** if `conversationId` is absent, `await createConversation(caseId, userId)` NOW (first message creates it — CONTEXT.md). Capture the id to return to the client (via a response header or the stream's final payload) so the client can hold it in zustand.
4. **streamText:** call `streamText({ model: anthropic(ANTHROPIC_MODEL), temperature: ASSISTANT_TEMPERATURE, system: buildSystemPrompt(role), tools: buildAssistantToolSet({ caseId, requestingUserRole: role }), messages: <converted useChat messages>, ... })`. Import the provider: `import { anthropic } from '@ai-sdk/anthropic'` (it reads ANTHROPIC_API_KEY from env — but we've already gated on isAssistantConfigured). Allow multi-step tool-calling (set the version's `maxSteps`/`stopWhen` so the model can call a tool then compose the answer). Pass `temperature: 0` and the pinned model id — determinism is a release blocker.
5. **Error-vs-decline separation (criterion 5 — CORRECTNESS CRITICAL):** wrap the streamText setup so that a provider/transport error (unreachable, timeout, auth) does NOT become streamed assistant text. Use the SDK's `onError` and/or wrap the initial call in try/catch: on a provider failure, return/emit the 503 ASSISTANT_UNAVAILABLE on the ERROR channel (an HTTP 503 if the failure happens before streaming starts; if mid-stream, surface it via the stream's error event, NOT as a text token). Set a request timeout (Claude's Discretion for the threshold — e.g. abort after ~20s) that trips ASSISTANT_UNAVAILABLE. A Decline must ONLY ever be the model's own grounded-fallback TEXT; the route must never synthesize "I don't have that information" on an error.
6. **Citation extraction + persistence (criterion 2):** in the SDK's `onFinish` callback, assemble the final assistant text and derive the `CitationInput[]` from the tool results produced this turn (record ids + timestamps + a human label like "Status change recorded Oct 6, 2026 2:14pm"). Map each tool's result shape to citations: ExhibitEvent (from getExhibitHistory timeline entries — eventId + recordedAt), DiscrepancyFlag (from getDiscrepancies — flag id + createdAt), JuryPackageExhibit (from getJuryPackageStatus rows). Then `await persistTurn({ conversationId, userMessage, assistantContent, citations })`. Also send the citations + conversationId to the client in the stream's final structured payload (so the UI renders pills without a second fetch) — use the SDK's message `data`/`annotations`/custom-data mechanism for the installed version. If the model Declined (no supporting tool records), citations is `[]` — persist the message with zero citations (valid Decline).
7. Return the SDK's streaming Response (`toUIMessageStreamResponse()` or equivalent), including the conversationId header so the client can capture a freshly-created conversation.

Keep the route thin: all data access is via the tool layer / services; NO direct Prisma queries for domain data here (only the assistant persistence service). Mirror the existing thin-route + `errorResponse` + `parseRequestingRole` conventions.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | useChat request body (messages, caseId, userId, conversationId) + X-User-Role header cross into the chat handler. |
| handler→LLM | Prompt + tool set cross to the Anthropic provider; the key must stay server-side. |
| LLM→DB | Model-composed content + extracted citations cross into the assistant tables. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-08 | Elevation of privilege | role spoofing via chat request to see sealed data | mitigate | Route derives role via `parseRequestingRole(request)` (fail-closed to ATTORNEY, 02-02) and passes it into `buildAssistantToolSet({requestingUserRole})`; the model cannot override it (04-02 ignores model-supplied role). Sealed exhibits never reach the model for an unauthorized role. |
| T-04-09 | Information disclosure | provider error leaking as assistant text / key leaking in error | mitigate | `onError`/try-catch routes provider/transport failures to the 503 ASSISTANT_UNAVAILABLE channel (never streamed text); no raw provider error (which could echo config) is forwarded to the client — `errorResponse` emits the fixed envelope. |
| T-04-10 | Spoofing/Repudiation | fabricated citation pointing at no real record | mitigate | Citations are extracted ONLY from THIS turn's tool results (real recordIds/timestamps from the service layer), never model-authored; `persistTurn` persists them so a grounded claim always has a traceable row; zero-ungrounded test asserts no factual sentence lacks a citation. |
| T-04-11 | Tampering | conversationId / IDOR on GET conversations/:id | accept | Demo has no per-user auth (single-case, zustand-only session; STATE.md 02-05 accepted risk T-02-07). Conversation ids are uuids; cross-user read is out of the v1 threat model. Owner: demo scope. Role-based sealed masking still applies to the DATA inside any conversation because every stored answer was already role-filtered at generation time. |
</threat_model>
