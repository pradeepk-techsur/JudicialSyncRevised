Create `src/stores/assistantStore.ts` following the roleStore zustand pattern (plain `create`, no persistence middleware — this is a browser-session store like the role store; CONTEXT.md "one continuous conversation per browser session"):

```typescript
import { create } from 'zustand';

interface AssistantState {
  isPanelOpen: boolean;
  activeConversationId: string | null; // null until the first message creates one server-side
  openPanel: () => void;
  closePanel: () => void;
  togglePanel: () => void;
  setActiveConversationId: (id: string) => void;
  // Explicit "New conversation" control AND the role-switch reset both call this:
  // clear the active conversation so the next message creates a fresh one and the
  // empty-state chips return. Prior conversations remain persisted server-side.
  newConversation: () => void;
}

export const useAssistantStore = create<AssistantState>((set) => ({
  isPanelOpen: false,
  activeConversationId: null,
  openPanel: () => set({ isPanelOpen: true }),
  closePanel: () => set({ isPanelOpen: false }),
  togglePanel: () => set((s) => ({ isPanelOpen: !s.isPanelOpen })),
  setActiveConversationId: (id) => set({ activeConversationId: id }),
  newConversation: () => set({ activeConversationId: null }),
}));
```

**Role-switch → new conversation (CONTEXT.md locked).** Edit `src/stores/roleStore.ts` `setActiveUser` so that when the role actually CHANGES, the active assistant conversation resets. To avoid a circular import, do NOT import assistantStore at module top in a way that risks a cycle — instead call it lazily inside setActiveUser:

```typescript
setActiveUser: (userId) => {
  const user = get().users.find((u) => u.id === userId);
  if (user) {
    const prevRole = get().role;
    set({ activeUserId: userId, role: user.role });
    if (user.role !== prevRole) {
      // Role change crosses a visibility boundary — start a fresh assistant
      // conversation so answers from different sealed-visibility scopes never mix
      // in one thread (CONTEXT.md; criterion 4 hygiene). Lazy require avoids a
      // static import cycle between the two stores.
      void import('@/stores/assistantStore').then((m) =>
        m.useAssistantStore.getState().newConversation(),
      );
    }
  }
},
```
(If a cleaner non-dynamic pattern fits the codebase — e.g. a tiny shared event or subscribing assistantStore to roleStore via `roleStore.subscribe` — use it and note the choice. The REQUIREMENT is: role change ⇒ activeConversationId becomes null.)

Requirements:
1. **Tagging.** Configure `useChat` so every request to `/api/assistant/chat` carries: the `X-User-Role` header (read `useRoleStore.getState().role`, same mechanism as apiClient — the role must be the CURRENT role at send time), and a body carrying `conversationId` (from `useAssistantStore.getState().activeConversationId`), `caseId` + `userId` (from `useRoleStore` — `caseId` and `activeUserId`). Use the installed SDK's transport/`prepareSendMessagesRequest` (v5+) or `body`/`headers` options to inject these per-request (not just once at init — role/conversation can change between sends).
2. **Capture conversationId (conversation-on-first-message).** When the server returns the conversationId for a freshly-created conversation (04-03 returns it via header or stream data), call `useAssistantStore.getState().setActiveConversationId(id)` so subsequent sends reuse the same thread. Before the first send, activeConversationId is null → server creates one → hook captures it.
3. **Load existing thread on mount (REPLAY path).** If `activeConversationId` is already set when the hook mounts (e.g. returning to the panel after navigating), seed `useChat`'s initial messages by fetching `GET /api/assistant/conversations/:id` (via apiFetch) and mapping ConversationDetail messages → useChat message shape. **Each mapped citation MUST carry `exhibitId` + `eventId` (and recordType/recordId/timestamp/label)** so a replayed pill deep-links exactly like a fresh-stream one — the GET response includes these (04-03). (Scroll preservation is a UI concern handled in 04-05.)
3b. **Surface citations with link fields on the FRESH stream path.** When a response streams in, map the citations carried in the stream's custom-data/annotations (per 04-03's SUMMARY) onto each assistant message so the UI reads them off `message` — and ensure `exhibitId` + `eventId` survive that mapping. **Expose a normalized `Citation { recordType, recordId, exhibitId, eventId, timestamp, label }` on each assistant message via the hook (same shape on BOTH the fresh-stream and GET-replay paths)** so 04-05's CitationPill reads `citation.exhibitId` / `citation.eventId` directly rather than re-deriving them. This is the client end of 04-01's additive columns + 04-03's wire contract.
4. **Outcome classification (three unambiguous outcomes — criterion 5 at the client).** Expose a derived `outcome` per assistant message / overall status: `'grounded' | 'decline' | 'unavailable' | 'streaming' | 'idle'`. Derivation rules:
   - `'unavailable'` when the request errored with HTTP 503 / the SDK `error` surfaced the ASSISTANT_UNAVAILABLE transport failure — this comes off the ERROR channel, NEVER from message text. Preserve the user's typed question (useChat keeps `input`/last user message; ensure a retry re-submits it).
   - `'decline'` when the completed assistant message has ZERO citations (a Decline — the model's grounded fallback text).
   - `'grounded'` when the completed assistant message has ≥1 citation.
   - NEVER classify an error as a decline: the 503/error path and the empty-citations path are distinct inputs. Add a code comment stating this is the client mirror of 04-03's error-vs-decline separation.
5. **Expose:** `{ messages, input, setInput, handleSubmit, sendExample(text), status, outcome, conversationId, newConversation, retry }`. `sendExample(text)` pre-fills + auto-submits an example chip (CONTEXT.md). `newConversation()` calls the store's reset AND clears useChat's local messages so the UI returns to the empty/chips state. `retry()` re-submits the preserved last user question (for the unavailable "Try again" button — no auto-retry loop).

Mark the file `'use client'`. Keep it free of presentation — pure state/behavior.
