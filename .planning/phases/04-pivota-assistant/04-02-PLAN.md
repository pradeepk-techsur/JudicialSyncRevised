<objective>
Build the server-side assistant tool layer — the 8 AI SDK `tool()` wrappers that are each a 1:1 pass-through to one existing service function — plus the cite-or-decline system prompt. This plan is the correctness keystone of Phase 4: it is where role-based sealed-exhibit visibility is enforced in the tool layer (criterion 4) and where the "never ungrounded" guarantee is anchored in the prompt.

Purpose: The tool set is the ONLY data path the LLM can touch; making every tool a thin pass-through to the identical service fn each UI screen already calls is what STRUCTURALLY guarantees the assistant and the dashboards can never drift. The sealed-seam gate is what makes an unauthorized sealed probe indistinguishable from a nonexistent exhibit.

Output: `src/lib/assistant/tools.ts` (buildAssistantToolSet), `src/lib/assistant/systemPrompt.ts` (buildSystemPrompt), and a hard integration test proving 1:1 wiring, sealed-invisibility, and zod rejection.
</objective>

  <name>Task 1: Build the 8 tool wrappers with role-scoped sealed seam</name>
  <files>src/lib/assistant/tools.ts</files>
  <action>
Create `src/lib/assistant/tools.ts`. Export `buildAssistantToolSet(ctx: { caseId: string; requestingUserRole: Role })` returning a `Record<string, Tool>` of the 8 AI SDK `tool()` definitions. Import `tool` from `ai`, `z` from `zod`, and the service functions. Each tool: a zod `inputSchema` + an `execute` that validates (zod does this via the SDK) then calls the ONE identical service fn — NO business logic, NO Prisma, NO second query path (FRD: "new logic goes in the service layer, never the tool wrapper").

EXACT tool contracts (TechArch 03-api.md §4.10 AssistantToolSet). Tool key names match the FRD Tool Set table:

1. **getExhibitStatus** — args `{ exhibitId: string }`. SEALED SEAM (see below) then `getExhibitStatus(exhibitId)` → `ExhibitCurrentState | null`.
2. **getUnresolvedObjections** — args `{ caseId: string }` (but IGNORE any model-supplied caseId that differs from ctx.caseId — always pass `ctx.caseId`; single-case demo). Calls `getUnresolvedObjections(ctx.caseId)` → `ObjectionCurrentState[]`, then FILTER OUT objections whose exhibit is sealed-and-unauthorized for `ctx.requestingUserRole` (see seam — case-wide variant).
3. **getCustodian** — args `{ exhibitId }`. SEALED SEAM then `getCustodian(exhibitId)` → `CustodyCurrentState | null`.
4. **getCustodyHistory** — args `{ exhibitId }`. SEALED SEAM then `getCustodyHistory(exhibitId)` → `CustodyHistoryEntry[]`.
5. **getExhibitHistory** — args `{ exhibitId }`. Calls `getExhibitHistory(exhibitId, ctx.requestingUserRole)` → `ExhibitHistoryResponse | null`. This service ALREADY applies the sealed seam internally (returns null for missing AND sealed-unauthorized), so NO extra gate needed — just pass the role. Its `timeline[]` entries (eventId/eventType/summary/recordedAt) are the ideal citation source.
6. **searchExhibits** — args map to `SearchExhibitsCriteria = { caseId; requestingUserRole; keyword?; status?; witness?; dateFrom?; dateTo? }`. Always set `caseId: ctx.caseId` and `requestingUserRole: ctx.requestingUserRole` (do NOT let the model override role — criterion 4). zod-optional the filter fields; `status` is the `ExhibitStatus` enum. `searchExhibits` already role-filters sealed via its service read AND throws `EMPTY_SEARCH_CRITERIA` 422 if no criterion — catch that and return `[]` (so the model declines) rather than throwing (a search with no criteria is just "no matching records" from the assistant's view).
7. **getJuryPackageStatus** — args `{ caseId: string; exhibitId?: string }`. Call Phase 3's `getJuryPackage(ctx.caseId, ctx.requestingUserRole)` → `{ juryPackage: JuryPackage | null; exhibits: JuryPackageExhibitView[] }`. If `exhibitId` is supplied, FILTER the returned `exhibits` to that exhibit (match on `exhibitId`), and return `{ juryPackage, exhibits: filtered }` — so "is Exhibit 14 in the jury package" resolves to that one row (or an empty exhibits array ⇒ not in package ⇒ model answers "no" / declines appropriately). The returned view is ALREADY role-filtered by the service (sealed rows dropped), so a sealed exhibit simply isn't present. Pass through whole when no exhibitId.
8. **getDiscrepancies** — args `{ caseId: string; exhibitId?: string }`. If `exhibitId` supplied: apply the SEALED SEAM for that exhibit, then call Phase 3's `getExhibitDiscrepancies(exhibitId)`; else call `getDiscrepancies(ctx.caseId)` (case-wide). Return `DiscrepancyFlag[]` (or `[]`).

**SEALED SEAM (criterion 4 — the single most important correctness item).** Four wrapped services (getExhibitStatus, getCustodian, getCustodyHistory, and the per-exhibit getExhibitDiscrepancies) do NOT take a role param, so calling them directly for a sealed exhibit would leak data to an unauthorized role. Implement a shared private helper in this file:

```typescript
import { getExhibit } from '@/services/exhibits';
// Returns true iff the exhibit is visible to this role. A sealed exhibit that the
// role cannot view returns false — INDISTINGUISHABLE from a nonexistent exhibit,
// because getExhibit applies canViewSealed as a WHERE predicate (02-02) and
// returns null for BOTH cases.
async function exhibitVisible(exhibitId: string, role: Role): Promise<boolean> {
  return (await getExhibit(exhibitId, role)) !== null;
}
```

For each exhibit-scoped tool that wraps a role-LESS service (tools 1, 3, 4, and the per-exhibit branch of 8): `execute` FIRST calls `exhibitVisible(exhibitId, ctx.requestingUserRole)`; if false, return the empty result for that tool's type (`null` for status/custodian, `[]` for custody-history/discrepancies) WITHOUT calling the underlying service — so the model receives nothing to cite and must Decline, byte-identical to a genuinely-missing exhibit. Do NOT throw, do NOT return an error string that hints at sealing.

For **getUnresolvedObjections** (case-wide, tool 2): after `getUnresolvedObjections(ctx.caseId)`, batch-resolve each objection's exhibit visibility and drop any whose exhibit is sealed-unauthorized. Simplest correct approach: collect distinct `exhibitId`s, `await Promise.all(ids.map(id => exhibitVisible(id, role)))`, build a visible-set, `filter`. (N is small — demo scope.)

**TOOL_ARGS_INVALID.** Use zod `.uuid()` on every `exhibitId`/`caseId` schema field. The AI SDK surfaces a schema validation failure back to the model as a tool error automatically — malformed args never reach the service/Prisma. Add a per-tool `execute` try/catch ONLY to convert an unexpected thrown AppError (other than the EMPTY_SEARCH_CRITERIA handled above) into a safe empty/null result or a `ToolArgsInvalidError`-shaped tool error, never an unhandled rejection that would crash the stream. Give each tool a clear `description` (one sentence, e.g. "Current lifecycle status of a single exhibit by id") so the model routes correctly.

Add rich JSDoc at the top stating the 1:1 pass-through contract and the sealed-seam rationale. Keep ZERO status/custody/objection derivation here — all shaping that the UI relies on already happened in the service layer.

Exact wording is Claude's Discretion (CONTEXT.md), but the prompt MUST encode ALL of:

1. **Identity/tone:** a courtroom clerk for case {role is for scoping, not naming} — confident, brief, factual. NO emoji, NO exclamation points, NO "Great question!"/filler. When grounded, state facts plainly and never hedge ("it appears…", "I think…").
