<objective>
Close CONFIRMED HIGH security finding F-09-01 (09-SECURITY.md): `POST /api/exhibits` → `createExhibit` has zero role enforcement today — any role, or no role header at all, can create a real exhibit record in a live case. This contradicts FRD `F20-server-side-role-enforcement-matrix.md` row 1 ("Create exhibit" restricted to DEPUTY/CLERK/ADMIN) and the Phase-9 threat register's now-disproven `accept` rationale ("no write endpoint exists... no server action to bypass" — live-exploit-tested false).

Add a server-side role gate to `createExhibit` mirroring the EXACT pattern `recordCustodyTransfer` already uses in `src/services/custody.ts:94-110` (08-02's shipped pattern) — resolve `actorUserId`'s `User.role` from the DB via Prisma and reject with the general-purpose `RoleNotPermittedError` (403) unless role ∈ {DEPUTY, CLERK, ADMIN}. This requires widening `createExhibit`'s signature to accept a required `actorUserId` and the route to accept/forward it — a real code change, not a no-op, since no role plumbing exists in this path today.

Per the locked 09-CONTEXT decision #1: do NOT introduce a new centralized `assertRole` helper, and do NOT extend role gating to any OTHER currently-ungated write path (status transitions, objection-raising) — this fix is scoped STRICTLY to `createExhibit`, exactly as F-09-01 calls for.

Purpose: an ad hoc per-service role check (the established pattern in this codebase — `custody.ts`, `objections.ts`, `discrepancies.ts`, `juryPackage.ts` all already do this independently) closes the one write path the Phase 9 security audit found genuinely exploitable, without requiring the deferred Phase 7.1 `assertRole`/Permission Matrix work.
Output: `createExhibit` is role-gated identically in spirit to `recordCustodyTransfer`; every existing caller (seed loader, service tests, route tests) is repaired to pass a DEPUTY/CLERK/ADMIN actor so the gate doesn't break legitimate fixtures.
</objective>

   // the ACTUAL User.role column, never a client claim, mirroring
   // custody.ts's recordCustodyTransfer pattern exactly. This was previously
   // the ONE confirmed-exploitable write path in the Phase 9 security audit:
   // any role (or no role header at all) could create an exhibit.

     where: { id: data.actorUserId },
     select: { role: true },

     throw new RoleNotPermittedError(
       'Only a courtroom deputy, clerk, or admin may create an exhibit',
