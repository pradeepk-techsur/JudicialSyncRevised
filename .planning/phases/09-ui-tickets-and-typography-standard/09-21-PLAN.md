<objective>
Fix the Case Workspace exhibit table's column layout, RE-CLOSING 09-UAT.md gap test 6 after the user's new report ("the description should be in line with all the other columns. all columns should show up in one row") showed 09-19's prior fix for this same table did not actually take effect.

**Root cause — independently re-derived in THIS plan's own investigation (not copied from 09-19's narrative), proven with four separate pieces of live evidence against a freshly rebuilt Docker container running the CURRENT working-tree source (no git history needed — the running container's `ExhibitTable.module.scss` was diffed byte-for-byte against the working tree first and confirmed identical):**

09-19's fix added this rule to `ExhibitTable.module.scss`:
```scss
.table :global(.cds--data-table) th:last-of-type.colChevron,
.table :global(.cds--data-table) td:last-of-type.chevronCell {
  inline-size: 2rem;
  width: 2rem;
}
```
The space between `.table` and `:global(.cds--data-table)` is a **descendant combinator** — it asks the browser to find a `.cds--data-table` element that is a **descendant of** (nested inside) a `.table` element. But Carbon's `<Table>` component renders ONE `<table>` element carrying **both** classes simultaneously (confirmed live: `document.querySelector('table').className` → `"cds--data-table _1e50fq_table cds--data-table--lg"` — one element, both classes, no nesting). A descendant combinator between two classes that live on the *same* element can never match anything.

**Proof, not inference** (all four checks run live against the rebuilt container at `http://localhost:3000/case`, Postgres seeded via `docker compose up -d db` + the app's own migrate+seed boot sequence):
1. `chevronTh.matches('.table :global(.cds--data-table)...')`-equivalent (`._1e50fq_table .cds--data-table th:last-of-type._1e50fq_colChevron`) → **`false`**. The 09-19 selector is dead code; it has never matched since it was written.
2. The compound (no-space) equivalent (`._1e50fq_table.cds--data-table th:last-of-type._1e50fq_colChevron`) → **`true`**.
3. Live DOM measurement with the CURRENT (dead-selector) CSS: chevron `<th>` width = **152px** (should be 32px / 2rem), Description `<th>` width = **152px** (should absorb the ~272px remainder) — Carbon's own unopposed `.cds--data-table th:last-of-type { inline-size: auto }` rule is still splitting the remaining table width ~50/50 between the chevron column and Description, exactly as it did before 09-19, because 09-19's guard never engaged.
4. Injecting the corrected compound selector via `page.addStyleTag` and re-measuring: chevron width → **32px**, Description width → **272px** (matches the hand-calculated remainder: 1136px table width − 864px of other fixed columns = 272px, exact). Rebuilding the Docker image with the ACTUAL file fix (not just an injected override) and re-measuring against the fresh container reproduced the identical 32px / 272px result and an identical full-page screenshot.

**Why this reads as "columns not in one row" (the user's new, more severe-sounding wording) rather than merely "a pill overflows":** with Description collapsed to 152px, its CSS `-webkit-line-clamp: 2` (`.descriptionCell`) forces even short descriptions like "Defendant's employment records" onto two wrapped lines inside a visibly narrow column sitting flush against a too-wide, empty-looking chevron column — at a glance this reads as "the row isn't laid out as one line of columns," which is what the user described, even though every `<td>` *is* technically still `display: table-cell` in one `<tr>` (verified: no responsive/stacked-table CSS, no `display:block`/`flex`/`grid` override anywhere in Carbon's data-table SCSS or this component applies at this breakpoint — ruled out directly by reading `node_modules/@carbon/styles/scss/components/data-table/_data-table.scss` in full: the only `display:flex`/`display:block` table-structure overrides are gated behind `.cds--data-table--sticky-header`, which this table does not use).

Also investigated and ruled out as contributing causes (per the gap's own investigation checklist): Carbon's `@carbon/react` `TableHeader`/`TableCell` components render real native `<th>`/`<td>` elements (confirmed by reading `node_modules/@carbon/react/es/components/DataTable/TableHeader.js` and `TableCell.js` source — both return a bare `jsx("th"/"td", ...)`, no div-based layout); there is no Carbon "stacked on narrow viewport" responsive mode active here (the sticky-header flex layout is opt-in via a `stickyHeader` prop this table does not pass, confirmed in `Table.js` source and in `ExhibitTable.tsx`'s `<Table className={styles.table}>` call site — no `stickyHeader` prop present).

Purpose: a pure CSS specificity bug (dead selector) from 09-19's own fix, not a data or component-logic defect — the fix is a one-token change (remove the space) to the exact same two selector lines 09-19 already added.
Output: the chevron selector becomes a real compound (same-element) selector that actually matches Carbon's DOM, restoring Description's full remainder width; the existing 09-19 Playwright regression test (`case-workspace.spec.ts`'s "zero cell-to-cell visual overlap" test) is extended with explicit column-width assertions precise enough that this exact dead-selector regression could never silently reappear and pass unnoticed again (09-19's test measured *overlap*, which happened to stay at zero by coincidence even with the broken selector in the specific seeded data — it never measured the chevron/description width split directly, which is why it passed 19/19 while the defect was live).
</objective>
