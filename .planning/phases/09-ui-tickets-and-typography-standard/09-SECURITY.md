## Resolved findings

### F-09-01: `POST /api/exhibits` had no role enforcement — **Fixed in 09-18, re-verified still fixed 2026-10-11**

- **Original finding (prior audit):** `createExhibit` had zero role check; any role (ATTORNEY, no header, etc.) could create a real exhibit row via `POST /api/exhibits`, contradicting FRD F20 row 1 (DEPUTY/CLERK/ADMIN only).
- **Fix verified at the code level (2026-10-10):**
  - `src/services/exhibits.ts:42` — `createExhibitSchema` now requires `actorUserId: z.string().min(1)`, producing a clean 422 (not a raw Prisma error) when absent.
  - `src/services/exhibits.ts:51` — `EXHIBIT_CREATE_ROLES = new Set(['DEPUTY', 'CLERK', 'ADMIN'])`, module-level, matching FRD F20 row 1 exactly.
  - `src/services/exhibits.ts:91-99` — after zod validation, before the `prisma.exhibit.create` write: resolves `actorUserId`'s **actual** `User.role` via `prisma.user.findUnique({ select: { role: true } })` — never trusts a client-supplied role/header — and throws `RoleNotPermittedError` (general-purpose class from `src/lib/errors.ts:75-79`, the same class `recordCustodyTransfer`/`acknowledgeDiscrepancy` use, not a private subclass) for any role outside the allow-set or a nonexistent user.
  - The mirroring of `src/services/custody.ts:94-110`'s `recordCustodyTransfer` pattern is faithful: same `Set`-based allow-list naming convention, same `prisma.user.findUnique({ select: { role: true } })` shape, same `!actor || !ROLES.has(actor.role)` short-circuit, same placement immediately before the write.
  - `src/app/api/exhibits/route.ts` required no change — it is a fully generic pass-through (`createExhibit(body as Parameters<typeof createExhibit>[0])`) that already forwards the full request body, so the new required `actorUserId` field and the role gate are both reached on every `POST` with no route-level gap.
- **Fix verified by live re-exploit** (2026-10-10 re-audit, against the running `project-app-1`/`project-db-1` stack, seeded case `2026-CR-0142`):
  ```
  POST /api/exhibits  actorUserId=<ATTORNEY user id>           → 403 ROLE_NOT_PERMITTED
  POST /api/exhibits  (no actorUserId field at all)             → 422 VALIDATION_ERROR ("actorUserId Required")
  POST /api/exhibits  X-User-Role: DEPUTY header + ATTORNEY actorUserId → 403 ROLE_NOT_PERMITTED (header cannot override the DB-resolved check)
  POST /api/exhibits  actorUserId=<nonexistent uuid>            → 403 ROLE_NOT_PERMITTED (no existence-enumeration leak)
  POST /api/exhibits  actorUserId=<DEPUTY user id>               → 201 Created (legitimate creation unaffected — no regression)
  ```
  Both original exploit vectors from the prior audit's transcript (ATTORNEY role, and no role header at all) are now blocked. Test artifacts created during verification were deleted immediately after (`prisma.exhibit.deleteMany({ where: { exhibitLabel: { startsWith: 'PWN-' } } })` and `'LEGIT-'`), leaving the seeded demo case clean.
- **Fix verified by the automated test suite (2026-10-10):** `docker compose exec app npx vitest run src/services/exhibits.test.ts src/app/api/exhibits/route.test.ts` → **39/39 passed**, including:
  - `exhibits.test.ts`: `'rejects exhibit creation by a non-DEPUTY/CLERK/ADMIN actor (e.g. ATTORNEY) with ROLE_NOT_PERMITTED'` — asserts `RoleNotPermittedError` AND zero rows created (`prisma.exhibit.count()` before/after).
  - `route.test.ts`: `'POST by an ATTORNEY actor returns 403 ROLE_NOT_PERMITTED'` and `'POST with no actorUserId returns 422 VALIDATION_ERROR'` — both direct route-handler-level proofs bypassing any UI.
- **No regression / no silent bypass confirmed (2026-10-10):** all 30 pre-existing `createExhibit(` call sites across `src/data/seed.ts` and 9 test files (`exhibits.test.ts`, `route.test.ts`, `activity.test.ts`+route test, `attentionFeed.test.ts`+route test, `custodyByCustodian.test.ts`+route test) were grepped and individually confirmed to supply a DEPUTY/CLERK/ADMIN `actorUserId` — none was found using a test-only bypass. Grepped `src/services/exhibits.ts` and `src/services/exhibits.test.ts` for `bypassRole`/`skipRoleCheck`/`TEST_MODE`/`__test`: 0 matches. `EXHIBIT_CREATE_ROLES` has exactly 2 references in the codebase (its definition and its one check call) — no second, weaker copy exists anywhere.
- **Scope discipline confirmed (2026-10-10):** per 09-CONTEXT decision #1, no centralized `assertRole` helper was introduced (grepped: 0 matches for `assertRole` anywhere in `src/`), and no other previously-ungated write path (status transitions, objection-raising) was touched — `git diff`-equivalent review of 09-18's file list confirms only `exhibits.ts` + seed/test fixtures were modified.
- **Regression re-check (2026-10-11, this incremental pass):** re-read `src/services/exhibits.ts` directly at current HEAD (not trusted from the prior report, given this phase's documented history of shared-working-tree hazards and the 09-19 dead-selector mistake). Confirmed byte-for-byte presence, unchanged, of: `EXHIBIT_CREATE_ROLES` Set (`:51`), the required `actorUserId` schema field (`:42`), the `prisma.user.findUnique` DB-role resolution (`:91-94`), the `RoleNotPermittedError` throw before the write (`:95-99`), and the unchanged pass-through route (`src/app/api/exhibits/route.ts`). `git log --oneline -- src/services/exhibits.ts` shows no commits touching this file since the original fix; `git status`/`git diff --stat HEAD` show a clean working tree. 09-21's two modified files (`ExhibitTable.module.scss`, `case-workspace.spec.ts`) are entirely outside the exhibit-creation code path. **No regression.**
- **Disposition:** CLOSED. No residual risk beyond the already-accepted T-09-13 architectural limitation (client-supplied `actorUserId` as an unauthenticated claim, mitigated by resolving the real `User.role` server-side on every write path that matters — the same accepted pattern as `recordCustodyTransfer`/`recordRuling`/`acknowledgeDiscrepancy`).
