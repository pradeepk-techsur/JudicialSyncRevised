Add a module-level constant mirroring the established pattern:

```typescript
const CUSTODY_WRITE_ROLES = new Set(['DEPUTY', 'CLERK', 'ADMIN']);
```

Insert the role check in `recordCustodyTransfer` AFTER the existing `INVALID_CUSTODIAN` check (the `toUser` lookup) and BEFORE the `$transaction` block — this ordering is deliberate and load-bearing: three existing tests pass a nonexistent/inactive user as BOTH `toCustodianUserId` AND `actorUserId` and expect `InvalidCustodianError` to fire first; placing the role check after the toUser lookup preserves that exact behavior unchanged.

```typescript
  // Server-side role gate (F24, Phase 8) — resolved from the ACTUAL User.role
  // column, never a client claim, mirroring objections.ts's recordRuling
  // pattern exactly. Reuses the general-purpose RoleNotPermittedError (not a
  // private ruling-specific subclass) per the locked CONTEXT decision. This is
  // the FIRST role enforcement custody.ts has ever had — previously ungated.
  const actor = await prisma.user.findUnique({
    where: { id: actorUserId },
    select: { role: true },
  });
  if (!actor || !CUSTODY_WRITE_ROLES.has(actor.role)) {
    throw new RoleNotPermittedError(
      'Only a courtroom deputy, clerk, or admin may propose a custody transfer',
    );
  }
```

Do NOT add any other role-gating in this file or elsewhere — `getCustodian`/`getCustodyHistory` remain unauthenticated reads, unchanged.
