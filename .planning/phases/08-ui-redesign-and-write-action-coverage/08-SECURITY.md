**Mode:** verify

## Summary

Phase 8 redesigns the UI (Trial Command Center, Exhibit Detail, Case Workspace, Jury Package Workspace) and adds exactly two new write actions to a previously read-mostly surface: a server-side role gate on `recordCustodyTransfer` (closing a previously-zero-enforcement gap) and a new `requestFinalization` notification path with an *inverted* role gate. All 27 named threats (T-08-01 through T-08-27) across the 15 plan files were walked against the actually-implemented code at HEAD — not the plans' claims — and every one was confirmed genuinely present.

The two highest-stakes `mitigate` dispositions were further confirmed **empirically against the live, running stack** (docker compose, real Postgres, real seeded case `2026-CR-0142`): (1) a direct `curl` POST to `/api/exhibits/:id/events/custody` with no role-appropriate actor returned a live `403 ROLE_NOT_PERMITTED`, proving T-08-04's new custody role gate is real and reachable, not merely unit-tested; (2) a direct `curl` POST to `/api/jury-package/:id/request-finalization` as a DEPUTY (a finalize-authorized role) returned a live `403 ROLE_NOT_PERMITTED` with the exact inverted-gate message, proving T-08-01's inverted role check is real. The sealed-visibility WHERE-predicate consistency across the three new Command Center read endpoints (T-08-10) was also empirically confirmed: the seeded sealed exhibit `S-1` is present in the `JUDGE`-role exhibit list and its custodian's group in `custody-by-custodian`, and is **structurally absent** (not redacted) from both when requested as `ATTORNEY` — a live demonstration of the same `canViewSealed(role) ? {} : { isSealed: false }` predicate pattern applied identically in `getCustodyByCustodian`, `getAttentionFeed`, and `getStatusCounts`.

The seed-only `legacyAdmitForDemo` gate-bypass helper (T-08-08) was confirmed confined to `src/data/seed.ts` by directly re-running the exact grep command the confinement test (`seed.test.ts`) encodes (`grep -rln "legacyAdmitForDemo" src --include="*.ts" --include="*.tsx"`, non-test files only) — it returned exactly `['src/data/seed.ts']`, matching the test's asserted expectation. (Vitest itself could not be executed in this sandbox due to a missing `vitest/config` module resolution in the ephemeral npx install; the underlying grep invariant the test encodes was instead reproduced directly and independently confirmed.)

The phase's own stated "absent-not-disabled" UI role-gating pattern was spot-checked against **five** consuming components (`RecordRulingForm`, `TransferCustodyForm`, `ObjectionCard`, `AttentionFeedPanel`, `CustodyAtAGlancePanel`) — exceeding the required 3 — and in every case the client-side absence is backed by a genuine, independently-resolved server-side role check (`recordRuling`'s `actor.role !== 'JUDGE'` DB lookup since Phase 1; `recordCustodyTransfer`'s new `CUSTODY_WRITE_ROLES` DB lookup from 08-02). No consuming component relies on the UI gate as its sole enforcement.

No unflagged HIGH/CRITICAL attack surface was found. One adversarial probe (multi-case / cross-case IDOR via a client-supplied `caseId`) was raised and refuted: no `GET /api/cases` listing or Case Selector exists in this phase (explicitly deferred to the unplanned Phase 7.1 stub per 08-CONTEXT.md), the seed loader provisions exactly one case system-wide, and the new Command Center endpoints apply the identical sealed-exclusion predicate as every pre-existing read regardless of which `caseId` is supplied — there is no broader exposure introduced by this phase's new routes than already existed. All `accept`/`transfer` dispositions were confirmed as legitimate, documented scope boundaries (pure rendering-only changes, demo-scale DoS non-issues, idempotent-SAFE double-click races) rather than lapsed mitigations dressed up as accepted risk.
