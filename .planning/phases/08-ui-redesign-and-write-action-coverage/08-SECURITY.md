## Summary

This is a re-audit. The prior audit (2026-10-09, HEAD `0a54948`) covered plans 08-01 through 08-15 — 27 named threats (T-08-01..T-08-27) plus 2 unnamed adversarial probes — all confirmed SAFE, verdict SECURED. That audit did not cover 08-16, a 2-task gap-closure plan that did not exist yet when it ran. This re-audit's scope is exactly the 08-16 delta: 5 files (`src/components/shell/Sidebar.module.scss`, `e2e/app-shell.spec.ts`, `src/components/command-center/StatusDistributionBar.tsx`, `src/components/command-center/StatusDistributionBar.module.scss`, `e2e/command-center.spec.ts`). None of these 5 files appear in any `Location` cell of the prior audit's 27-row attack-surface table — there is zero file overlap between the two audits' scopes, so all 27 prior findings are carried forward unchanged below, cited to the prior audit rather than re-derived.

08-16 is a CSS-positioning fix (sidebar/header stacking-context overlap) plus a markup-removal (deleting a segmented status-distribution bar, keeping its legend) plus accompanying Playwright test updates. Direct source review confirms both production changes are exactly what their SUMMARY and PLAN claim and introduce no new attack surface: (1) `Sidebar.module.scss`'s `inset-block-start: 3rem` / `block-size: calc(100% - 3rem)` are static, compile-time SCSS values with no runtime interpolation from any user-controlled input — there is no injection vector in a CSS Module, and the offset only affects the already-authorized, already-visible nav links' paint position, with no z-index change and no effect on any overlay/clickjacking-relevant stacking order elsewhere in the shell (confirmed no z-index touched, only `inset-block-start`/`block-size`). (2) `StatusDistributionBar.tsx` was traced end-to-end: its sole prop, `statusCounts`, is passed unchanged from `src/app/command-center/page.tsx:70,118` (`activity.data?.statusCounts`), which in turn comes from `useRecentActivity()` (`src/hooks/useRecentActivity.ts`) querying `GET /api/cases/:id/activity`, which calls the exact same `getStatusCounts(caseId, requestingUserRole)` service function that 08-06/08-10 already sealed-filter server-side (per prior audit T-08-10, unchanged in this delta). 08-16 removed only a `<div>` bar wrapper and an unused `total` reduce; it added zero new queries, zero new hooks, zero new props, and zero client-side re-derivation from a broader dataset — the legend-only component receives the IDENTICAL already-filtered `Record<ExhibitStatus, number>` shape as before. The two e2e spec files were diffed for removed assertions: `e2e/app-shell.spec.ts` only ADDED a new bounding-box/hit-test regression test (no existing assertion removed); `e2e/command-center.spec.ts` replaced a single `toBeVisible()` check on the now-deleted bar element with two explicit `toHaveCount(0)` permanent-absence assertions — no role-gating, authz, or sealed-visibility assertion was touched or weakened in either file (confirmed by reading all `role`/`getByLabel`/`toHaveCount` occurrences in both files).

08-16's own `<threat_model>` registered its claim as `T-08-18` ("Information disclosure... accept... no new or reduced data exposure") — this ID collides with the prior audit's unrelated `T-08-18` ("`ExhibitTable`'s sealed pill reveals nothing new", from 08-10-plan). This re-audit flags the collision as an audit-trail hygiene defect (see Audit trail) but independently verified the SUBSTANCE of 08-16's claim regardless of the ID collision, assigning it a non-colliding ID (`T-08-28`) below. The claim holds: confirmed by direct data-flow trace, not accepted on the plan's assertion alone.

A live stack was running at audit time (`curl` to `http://127.0.0.1:3000` returned `307`, the expected `/`→`/command-center` redirect). A light live check (`GET /` rendered HTML) confirmed the sidebar/header markup renders as expected in the current build; a full role-differentiated live probe of `/command-center` was not re-run since 08-16 made no backend/data changes and the static trace above is conclusive for a CSS/markup-only diff — consistent with the task's guidance that static review is sufficient here.

No new HIGH/CRITICAL (or any severity) finding was introduced by 08-16. Verdict remains SECURED.
