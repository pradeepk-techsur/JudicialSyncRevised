Carbon API notes verified during planning (checked against `carbon-design-system/carbon` main-branch component source):
- Carbon's `Select` component (`import { Select, SelectItem } from '@carbon/react'`) renders a REAL `<select>` with a REAL `<label htmlFor={id}>` — confirmed by reading its source directly. This is the ONLY Carbon form component that wraps a native `<select>`; Carbon's `Dropdown` is a custom downshift-based listbox (`<button>` + `<li role="option">` popup), which would NOT satisfy `app-shell.spec.ts`'s `select.locator('option:checked')` / `select.locator('option', { hasText: 'ATTORNEY' })` assertions (those require literal DOM `<option>` elements inside a literal `<select>`). Use `Select`/`SelectItem`, NOT `Dropdown`, for the role switcher — this is a hard requirement, not a style preference.
- `Select` takes `labelText` (rendered as a real `<label>`) and `id` (used for the `htmlFor` association) — Playwright's `getByLabel('Switch active role')` resolves via this real label/for pairing (the current implementation achieves the same thing via a wrapping `<label>` element; Carbon's `Select` renders the same association, just internally). Set `labelText="Role:"` to preserve the exact visible "Role:" prefix text currently shown, and `id="role-switcher"` (or similar) — but the ACCESSIBLE NAME Playwright matches on must be exactly `"Switch active role"`, so pass that as `aria-label` on the underlying `<select>` via... Carbon's `Select` does not expose a direct `aria-label` override prop distinct from `labelText` in all versions — if `labelText` becomes the only accessible-name source, set `labelText="Switch active role"` and `hideLabel` to `false` is wrong (it would show "Switch active role" as visible text instead of "Role:"). The correct approach: check the installed `@carbon/react` version's `Select` props for an `aria-label`-passthrough (rest-prop spreading onto the `<select>` — the source shows `{...other}` spread onto the underlying `<select>` element, so passing `aria-label="Switch active role"` as a prop on `<Select>` should land on the real `<select>` and take precedence as the accessible name over the visible `<label>` text, matching current behavior exactly where the visible label says "Role:" but the accessible name is "Switch active role"). Verify this with a quick rendered-DOM check during Task 1 before relying on it in Wave 3 testing.
- Carbon's UI Shell components: `Header`, `HeaderName`, `HeaderGlobalBar`, `HeaderGlobalAction`, `SideNav`, `SideNavItems`, `SideNavLink`, `Content` (from `@carbon/react`) are the canonical "UI shell header" / "UI shell left panel" patterns (see carbondesignsystem.com Building Blocks → Components → "UI shell header" / "UI shell left panel"). Use them for the overall shell composition.
- `HeaderGlobalAction` renders a `<button>` with an icon + `aria-label` — ideal for the "Ask ✦" button (`data-testid="ask-assistant"` must still be set as a rest-prop, `aria-label="Open Pivota Assistant"` preserved).
- `SideNavLink` accepts `href`/`isActive`/`renderIcon`, rendering an `<a>` under the hood (compatible with Next.js's `Link` via the `as`/`element` prop or by wrapping — check the installed version's exact composition prop; Carbon's own Next.js integration docs recommend passing `element={Link}` or `as={Link}` where supported, falling back to a plain `<a>` + `next/link`'s `legacyBehavior` pattern, or simplest: keep using `next/link`'s `<Link>` directly as the rendered element and apply Carbon's `cds--side-nav__link` class manually if `SideNavLink`'s own `element` prop isn't available in the installed version — resolve this by checking `@carbon/react`'s installed `SideNavLink` props at execution time, since this is exactly the kind of "verify current API, don't guess" situation called out in this project's research conventions).
