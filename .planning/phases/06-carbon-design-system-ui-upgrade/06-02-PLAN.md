<objective>
Migrate the three cross-screen SHARED presentational components — `StatusBadge`, `DiscrepancyBadge`, `AcknowledgeInline` — from hand-rolled Tailwind spans/buttons to IBM Carbon Design System primitives (`Tag`, `TextArea`, `Button`). These three components are imported identically by multiple Wave 3 screen plans (Case Workspace, Exhibit Detail, Jury Package) — migrating them here, in Wave 2, means every Wave 3 screen plan picks up the Carbon versions for free instead of each screen reimplementing status/discrepancy/acknowledge rendering independently (which would reintroduce the exact drift risk US-1.2/US-6.3 exist to prevent).

Purpose: Preserve the single-shared-component structural guarantee (status can never visually differ across screens; discrepancy acknowledgment can never be silently hidden) while swapping only the rendering layer to Carbon.
Output: Three Carbon-based shared components, each behaviorally and attribute-for-attribute identical to their Tailwind predecessors (same data-testid, same aria-label text, same conditional logic), ready for Wave 3 screens to import unchanged (same import paths, same prop signatures).
</objective>

Carbon API notes verified during planning (Carbon's `Tag` component source, `carbon-design-system/carbon` main branch):
- `Tag` accepts `type` (color: one of `red`/`magenta`/`purple`/`blue`/`cyan`/`teal`/`green`/`gray`/`cool-gray`/`warm-gray`/`high-contrast`/`outline`), renders as a plain `<div>`-like static element when no `onClick`/interactive props are given (exactly the static, non-interactive rendering StatusBadge and DiscrepancyBadge need — these are never clickable).
- `Tag` has no built-in "dot" visual — the colored dot convention (`●ADMITTED`) from Y0-patterns.md is preserved by rendering a small colored `<span aria-hidden>` dot INSIDE the Tag's children, exactly as the current implementation already does inside its own `<span>` wrapper (just swap the outer wrapper element for `<Tag>`).
- Y0-patterns.md explicitly calls out: "implemented as a Carbon `Tag` using Carbon's status-color tokens as of Phase 6" for StatusBadge, and the Discrepancy Flag Treatment pattern calls for "Amber/warning-colored badge ... always visible" — Carbon's closest token color for "amber/warning" is `type="gray"` is NOT it; Carbon ships no literal "amber" Tag type, so use CSS override via a thin wrapper class (see Task 2) applying Carbon's own `$support-warning` token color, OR simpler: Carbon Tag doesn't have an amber built-in type, but IBM's own Notification/warning convention commonly maps to `type="gray"` with a custom warning-icon — for DIRECT visual fidelity to the existing product (amber-800/amber-50/amber-200 Tailwind classes), apply a small scoped CSS Module (`DiscrepancyBadge.module.scss`) that overrides the Tag's background/border/text color to Carbon's `$support-warning`/`$yellow` SCSS tokens while keeping every other Tag behavior (ellipsis handling, sizing, DOM structure) from the component itself. This is the same pattern Carbon itself recommends for "status indicators that need a color the built-in Tag `type` enum doesn't cover" (see Carbon's own "Status indicators" pattern page under Building Blocks → Patterns).
