Carbon component mapping for this screen:
- Keyword search input → Carbon `Search` (`labelText`/`aria-label="Keyword search"`, `placeholder="Search exhibits…"`) — Carbon's `Search` is purpose-built for exactly this (has its own clear-button affordance too).
- Status filter → Carbon `Dropdown` (NOT `Select` — see above), `aria-label="Filter by status"`, `titleText` hidden via `hideLabel` if a visible label isn't wanted inline, `items={STATUS_OPTIONS}` with `id`/`titleText` required props.
- Witness text input, date-from/date-to inputs → Carbon `TextInput` (witness) and Carbon `DatePicker`/`DatePickerInput` (dates) OR, if `DatePicker` introduces a dependency on Carbon's `flatpickr`-based calendar widget that changes the native `type="date"` picker UX in a way that risks behavioral drift from the current plain `<input type="date">`, keep plain `TextInput` with `type="date"` (Carbon's `TextInput` forwards the native `type` prop) — this is the safer, lower-risk choice for a pure styling migration with a "no behavior change" constraint; prefer `TextInput type="date"` over introducing `DatePicker`'s richer (and different) interaction model.
- Filter chips (removable, "witness=Smith ×") → Carbon `DismissibleTag` (the modern replacement for `Tag filter` — `Tag`'s own `filter` prop is deprecated per Carbon's current source, so use `DismissibleTag` directly, with its `onClose` callback wired to the existing per-key removal logic).
- "Clear filters" → Carbon `Button kind="ghost" size="sm"`.
- The exhibit table itself → Carbon's STATIC `Table`/`TableHead`/`TableRow`/`TableHeader`(or `TableCell` in the header)/`TableBody`/`TableCell` (the plain composable primitives, NOT the stateful `DataTable` render-prop component — this screen has no sorting/batch-selection/pagination today and adding any would be a functional change out of scope for this phase).
