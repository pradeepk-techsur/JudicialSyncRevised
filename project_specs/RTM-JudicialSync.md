## 1. Overview

This Requirements Traceability Matrix (RTM) provides bidirectional traceability across every layer of the JudicialSync specification set — from the 24 PRD features (F0–F23, following the Phase 7 addition of F12–F15 and the Phase 7.1 INSERTED addition of F16–F23), through their corresponding FRD functional chunks (F00–F23), into the TechArch components, data model, and API surface that implement them, and finally into the UserStories epics and acceptance criteria that define how each requirement will be verified. Its purpose is to make certain that every product requirement has a documented implementation path and that every implementation artifact traces back to an approved requirement — nothing is built that wasn't specified, and nothing specified is left unimplemented or untested.

JudicialSync is architecturally simple by design: a single append-only event ledger (`exhibit_events`), a small set of derived current-state projections, one shared service layer, and a fixed (≤8-tool) assistant tool set that wraps that same service layer 1:1. Because of this architecture, traceability in this project is unusually tight — each PRD feature maps to exactly one FRD chunk, which maps to a small, enumerable set of TechArch tables/services/endpoints, which in turn maps to one or two UserStories epics. There are no orphaned requirements and no parallel implementation paths to reconcile. This RTM documents that 1:1 structure explicitly so it can be validated during implementation and QA rather than assumed.

JudicialSync does not yet have a dedicated FIPS (Feature Implementation Plan/Spec), BusinessCase, or CostBenefitAnalysis document generated in `project_specs/` at the time of this RTM's creation; this matrix covers the documents that exist (PRD, FRD, TechArch, UserStories, and — as of the Phase 7 update — JOURNEYS, STORY-MAP, and UX-Mockup) and should be regenerated or extended if FIPS/BusinessCase/CostBenefitAnalysis are produced later.

**Phase 7 update (2026-10-08):** This RTM was extended to cover Phase 7 — "Fix admission integrity and UI usability issues" (`.planning/ROADMAP.md`) — which added four PRD features (F12–F15), their FRD chunks, their TechArch amendments, and 14 new UserStories (US-12.1–US-15.5, Epics 12–15). Traceability levels covered in this document:
- **Level 1 — PRD → FRD:** Every PRD feature (F0–F23) maps to exactly one FRD functional chunk of the same number (F00–F23), confirming no feature was dropped or silently re-scoped during functional elaboration.
- **Level 2 — FRD → TechArch:** Every FRD chunk's data model, service-layer functions, and API surface are traced to the specific TechArch section (data model §3, component §2, API §4, security §5) that implements it.
- **Level 3 — TechArch → UserStories:** Every TechArch component/table/endpoint is traced to the UserStories epic(s) whose acceptance criteria exercise it, confirming test coverage exists for every implemented capability.
- **Level 4 — Test Coverage:** Acceptance criteria within each UserStories epic are treated as the atomic, countable test-case units for this project (no separate TEST-XXX catalog exists yet), and are tallied per feature in §5 below.
- **Level 5 — UserStories → Journey/UX-Mockup (Phase 7 and Phase 7.1 only):** Each of the 14 Phase 7 UserStories is additionally traced to its JRN-02.1 (or JRN-01.1/JRN-01.2) journey-stage touchpoint and UX-Mockup screen in §3a; each of the 24 Phase 7.1 UserStories is likewise traced to its JRN-02.1/JRN-01.2/JRN-03.1/JRN-04.1 journey-stage touchpoint and UX-Mockup screen in §3b.

## 2. Requirements Summary

- **24 PRD features (F0–F23)** span six categories: Data Foundation (1), Status Tracking (9, with Phase 7's F12 and Phase 7.1's F16/F17/F18/F19 added), Differentiator (5, with Phase 7's F13/F14 and Phase 7.1's F23 added), UI Screen (6, with Phase 7.1's F21 added), Usability (2, with Phase 7's F15 added), and Security/Scope Reversal (2, Phase 7.1's F20/F22) — see PRD §9 Feature Index.
- **17 P0 (Critical/MVP) features:** F0, F1, F2, F3, F5, F6, F7, F9, F10, F11, F12, F13, F16, F17, F18, F19, F20 — these collectively form the minimum viable demo plus the Phase 7 integrity gates (F12, F13) and the Phase 7.1 structural-integrity gates (F16–F20); none can be cut without breaking the core "judge asks a live question" scenario or reopening the admission/sealed-exhibit/custody/authorization gaps Phase 7 and Phase 7.1 close.
- **7 P1 (High) features:** F4 (Exhibit Search), F8 (Trial Command Center Screen), F14 (Discrepancy Acknowledgment Transparency), F15 (Courtroom Usability Fixes), F21 (Pending-Ruling Queue), F22 (Multi-Case Support with Case Selector), F23 (Versioned Jury Packages with PDF Export) — materially improve usability/trust/ambient awareness/sales-demo breadth but are not blocking for the Q&A/status core scenario.
- **24 FRD functional chunks (F00–F23)** map 1:1 to PRD features, plus **5 cross-cutting FRD chunks (Y0–Y4)** covering schema, API, error catalog, integrations, and the Phase 6 design-system migration that are referenced (not duplicated) by every feature chunk.
- **9 core domain tables + 3 assistant-audit tables** defined in TechArch §3 Data Model: `cases`, `users`, `exhibits`, `exhibit_events` (the ledger), `exhibit_current_state`, `objection_current_state`, `custody_current_state`, `discrepancy_flags`, `jury_packages`, `jury_package_exhibits`, `assistant_conversations`, `assistant_messages`, `assistant_citations`. **Phase 7 (F13) amended** `jury_package_exhibits` with `status`/`excluded_at`/`excluded_by`/`exclusion_reason` and added the `JURY_PACKAGE_EXHIBIT_EXCLUDED` event type. **Phase 7.1 (TechArch §3.10) adds, in a single combined migration:** a new `ExhibitClassification` enum plus a required `exhibits.classification` column (F16); three new `EventType` enum values (`CUSTODY_TRANSFER_PROPOSED`/`CONFIRMED`/`CANCELLED`) plus three new nullable `custody_current_state` columns (`pending_transfer_to_user_id`, `pending_transfer_event_id`, `pending_transfer_proposed_at`) (F19, and F18 indirectly via its intake-bootstrap event type); and a new nullable `jury_packages.version` column with a `(case_id, version)` unique constraint (F23). F17, F21, and F22 are confirmed, explicitly, to introduce **no** schema change.
- **1 non-negotiable architectural constraint** underlies every requirement: status, objections/rulings, and custody are modeled exclusively as append-only ledger events, never mutable fields — enforced from PRD §4 through FRD's cross-cutting terminology through TechArch §1.3/§3 and verified by UserStories US-0.3.
- **~27 REST/streaming API endpoints** documented in TechArch §4 (Phase 7 added one new route, `POST /api/jury-package/:id/exhibits/:exhibitId/exclude` (F13), and amended two existing ones. **Phase 7.1 adds 7 new routes** — `GET /api/cases` (F22), `GET /api/cases/:id` replacing `GET /api/case` (F22), `POST /api/exhibits/:id/events/custody/propose`, `/confirm`, `/cancel` (F19), `GET /api/cases/:id/jury-package/versions`, `GET /api/jury-package/:id/export` (F23) — and amends `POST /api/exhibits` (F16, F20), `POST /api/exhibits/:id/events/status` (F18, F20), `POST /api/exhibits/:id/events/objection` (F20), `GET /api/cases/:id/objections?status=unresolved` (F21), `POST /api/exhibits/:id/events/custody` (F19), `GET /api/exhibits/:id/custodian`/`custody-history` (F19), `POST /api/cases/:id/jury-package`/`GET` (F16), and `POST /api/jury-package/:id/finalize` (F23) — each traced to its originating FRD feature chunk and consumed by exactly one UI screen and/or one assistant tool — never a parallel, divergent access path.
- **8 assistant tools** (`getExhibitStatus`, `getUnresolvedObjections`, `getCustodian`, `getCustodyHistory`, `getExhibitHistory`, `searchExhibits`, `getJuryPackageStatus`, `getDiscrepancies`) are each a 1:1 pass-through to an identically-named service-layer function — the structural guarantee that the assistant can never state something a UI screen doesn't also show. Phase 7's F13/F14 amendments and Phase 7.1's F16/F19 amendments propagate to `getJuryPackageStatus`/`getDiscrepancies`/`getCustodian`/`getCustodyHistory` automatically via this same mapping. The assistant's 8 tools remain read-only and are confirmed unaffected by Phase 7.1's F20 permission matrix (US-20.6) and F22's multi-case scoping (caller-supplied `caseId` was already a required tool input per F07).
- **24 UserStories epics, 69 user stories total** (46 P0, 21 P1, 2 P2) — see UserStories Summary Table — collectively carrying **256 acceptance criteria**, the atomic test-case units tracked in §5 below. Phase 7 added 4 epics (12–15), 14 stories, 55 acceptance criteria. **Phase 7.1 adds 8 epics (16–23), 24 stories (16 P0, 8 P1, 0 P2 at the epic-list level above the story grain — see §5 for the exact per-story priority breakdown), 94 acceptance criteria**.
- **8 Non-Functional Requirements** (PRD §6) — Trustworthiness over fluency, Single source of truth, Auditability, Role-appropriate visibility, Responsiveness for live use, Demo reliability, Non-technical usability, Realistic seed data complexity, plus the Phase 6-added Design-system foundation NFR — each traced to a specific TechArch enforcement mechanism in §4 below.
- **2 discrepancy rules required at launch** (`ADMITTED_NO_CUSTODIAN`, `UNRESOLVED_OBJECTION_JURY_ELIGIBLE`), extensible per FRD F06, each independently traced from PRD F6 through TechArch §3.5 to UserStories US-6.1/US-6.2. **Phase 7's F12 closes the gap these two rules left open** by converting both conditions from a post-hoc discrepancy flag into a hard pre-write admission gate — F6's rules remain in force for conditions arising *after* a valid admission. **Phase 7.1's F18 moves the custodian half of this gate even earlier** (to the exhibit's first-ever `MARKED` transition, not just `ADMITTED`), and **F17 formally names, with dedicated regression coverage, the already-structural guarantee that F12's gate cannot be bypassed by an un-ruled objection** — F17 introduces no new runtime mechanism of its own.
- **One explicit, canonical server-side Permission Matrix (10 actions, TechArch §5.2.2a) introduced by Phase 7.1's F20**, superseding the partial pre-Phase-7.1 ad hoc checks (§5.2.2, retained for history) — every write action in the system now resolves the acting user's role from the database via a single shared `assertRole` helper, never from a client-supplied claim, traced from PRD F20 through TechArch §5.2.2a/§5.2.2b to UserStories US-20.1–US-20.6.
- **Phase 7 adds a Journey/UX-Mockup traceability layer (§3a)** not present for F0–F11: all 14 Phase 7 stories are traced to their JRN-02.1 (or, where applicable, JRN-01.1/JRN-01.2) journey-stage touchpoint and their UX-Mockup screen (Screen-00 through Screen-04). **Phase 7.1 adds a second such layer (§3b)** for all 24 new stories, spanning JRN-02.1 (two widened stages plus one new stage, "Confirm Custody Receipt"), JRN-01.2 (new stage "Check the Pending-Ruling Queue"), JRN-03.1 (existing stage annotated for F20), and JRN-04.1 (new stage "Switch Cases and Confirm Isolation"), and their UX-Mockup screens (`00-overview.md`, Screen-01, Screen-02, Screen-03, and the new sixth screen, `Screen-05-pending-ruling-queue.md`).

## 4. Requirements Detail

### P0 (Critical — MVP) Features

- **F0 — Exhibit Workspace (Data Model):** Foundational exhibit identity + append-only event ledger that every other feature depends on. FRD F00 locks this in as the sole source of truth (no mutable status/custody fields ever exist on `Exhibit`). Includes the deterministic seed-data loader with deliberately planted edge cases (unresolved objection, custody gap, jury-package discrepancy).
- **F1 — Exhibit Status Display:** At-a-glance lifecycle status (`MARKED`→`OFFERED`→`OBJECTED`→`ADMITTED`/`EXCLUDED`/`WITHDRAWN`), derived from `exhibit_current_state`, consistent across all four screens and the assistant.
- **F2 — Objection and Ruling Tracking:** Independent, concurrently-open objection threads per exhibit; `SUSTAINED`/`OVERRULED`/`RESERVED` rulings restricted to `JUDGE` role; feeds F1 status gating and F6 discrepancy detection.
- **F3 — Custody Tracking:** Custody transfers recorded as discrete immutable events (never a mutable "current holder" field); instant custodian lookup and full chain-of-custody retrieval; feeds F6's `ADMITTED_NO_CUSTODIAN` rule.
- **F5 — Jury-Ready Exhibit List Generation:** Computes jury-eligible candidates (`ADMITTED` status only) with F6 discrepancy detection as a hard, non-bypassable gate before finalization; finalization re-evaluates discrepancies fresh, never from a cached draft-time annotation.
- **F6 — Discrepancy Identification:** Two required rules at launch (`ADMITTED_NO_CUSTODIAN`, `UNRESOLVED_OBJECTION_JURY_ELIGIBLE`), auto-detected after every relevant ledger write, with an explicit, justified, ledger-recorded acknowledgment flow — never silently created or dropped by a user.
- **F7 — Pivota Assistant (Natural-Language Q&A):** The feature the entire demo depends on. Tool-calling only (no RAG/embeddings); cite-or-decline system prompt; role-scoped identically to UI; explicit, visually-distinct outage fallback (`ASSISTANT_UNAVAILABLE`, 503) separate from a Decline Response.
- **F9 — Case Workspace Screen:** Primary browsing/search surface; render-only (no embedded business logic); inline discrepancy indicators; sealed exhibits simply absent (never shown redacted) for unauthorized roles.
- **F10 — Exhibit Detail View Screen:** Complete chronological timeline reconstructed from the ledger, one entry per `ExhibitEvent`, no truncation; sealed exhibit for an unauthorized role returns 404 (not 403), identical to a genuinely nonexistent exhibit.
- **F11 — Jury Package Workspace Screen:** Authoritative handoff view; "Finalize" control is disabled (not just error-returning) while any open discrepancy remains; becomes fully read-only/export-ready once `FINALIZED`.
- **F12 — Admission Integrity Gating *(Phase 7)*:** Converts F6's two post-hoc discrepancy rules into a hard pre-write gate — an `ADMITTED` transition is rejected (422 `ADMISSION_BLOCKED`, all applicable reasons listed at once) rather than silently recorded, when an unresolved objection or missing custodian is present; enforced once inside the shared status-transition service with no override, bypass flag, or elevated-role exception for any caller (UI, API, or seed loader).
- **F13 — Jury Package Ex Parte / Sealed Exclusion *(Phase 7)*:** The highest-severity fix in this release — a hard, query-level exclusion ensuring a sealed/ex-parte exhibit can never acquire an `INCLUDED` jury-package row or a `CLEAN` discrepancy status, regardless of its admission status; includes an auditable "Remove from Package" remediation path (`JURY_PACKAGE_EXHIBIT_EXCLUDED` event) for any legacy/regression row found already present.
- **F16 — Exhibit Classification Taxonomy *(Phase 7.1)*:** Replaces the `isSealed` boolean's role as the authoritative sensitivity input with a formal, required, intake-time, immutable three-value enum (`TRIAL`/`CHAMBERS_EX_PARTE`/`SEALED`); `isSealed` is retained only as a write-once, classification-derived mirror so every existing visibility/exclusion call site remains unchanged in behavior while gaining the ability to distinguish chambers-ex-parte from sealed material for the first time.
- **F17 — Objection-to-Admission State-Machine Hardening *(Phase 7.1)*:** A "no new mechanism" feature by design — formally names, and adds dedicated regression coverage for, the guarantee that F12's existing Admission Gate already and unconditionally prevents any `OBJECTED → ADMITTED` transition without an intervening ruling event, since `ObjectionCurrentState.status` has no other write path out of `UNRESOLVED`; confirms the legal direct `OFFERED → ADMITTED` path for never-objected exhibits remains unaffected.
- **F18 — Custodian Required at Intake (MARKED) *(Phase 7.1)*:** Moves the custodian requirement from F12's admission-time check to the exhibit's very first status transition — the `STATUS_CHANGE` (`(none) → MARKED`) and the resulting `CUSTODY_TRANSFER_CONFIRMED` event are written atomically in one transaction, closing the custody-gap window that previously existed between intake and admission; F12's later admission-time check is retained unchanged as an independent backstop.
- **F19 — Custody Handoff Confirmation *(Phase 7.1)*:** Converts the unilateral custody-transfer action into a two-phase propose/confirm ledger-event model — current custody changes only when the exact named receiver confirms, never on the proposer's assertion alone; a pending transfer is visibly distinct from a confirmed one, and a pending-but-unwanted transfer can be explicitly cancelled; the exhibit's first-ever custody link (F18) is a documented, single-phase bootstrap exception to this model.
- **F20 — Server-Side Role Enforcement Matrix (Full RBAC) *(Phase 7.1)*:** Extends server-side role checking — previously applied only to rulings, jury-package finalization, and discrepancy acknowledgment — to every write action in the system under one explicit, canonical permission matrix (10 actions), enforced by a single shared `assertRole` helper that resolves the acting user's role from the database, never from a client-supplied claim; this is an explicit, traceable reversal of the PRD's and TechArch's prior "full auth hardening out of scope" note, narrowed to confirm only *authentication* (not authorization) remains out of scope.

### P1 (High) Features

- **F4 — Exhibit Search:** Combinable (AND-semantics) filters by ID, keyword, status, witness, date range; surfaced identically in Case Workspace UI and via the assistant's `searchExhibits` tool.
- **F8 — Trial Command Center Screen:** Ambient, read-only, passive-monitoring view (Recent Activity / Unresolved Objections / Discrepancies panels); composes existing F2/F3/F6 service functions with zero new business logic; link-through only, no data entry.
- **F14 — Discrepancy Acknowledgment Transparency *(Phase 7)*:** A pure UI-visibility requirement layered on F6's unchanged acknowledgment data model — makes role-eligibility, the permanent-record framing of the justification field, and the full acknowledgment audit record (actor/role/timestamp/justification) visible at the point of action on every screen that renders a discrepancy flag, with no new data capability, API contract, or schema change.
- **F15 — Courtroom Usability Fixes *(Phase 7)*:** Five client-rendering corrections against data the service layer already returns correctly — fully clickable Case Workspace rows, assistant example prompts sourced from real seeded exhibit labels, a labeled-or-removed header element, and date-qualified, exhibit-labeled activity-feed rows; none requires an API contract, service-layer, or schema change.
- **F21 — Pending-Ruling Queue *(Phase 7.1)*:** A new, judge-role-restricted screen listing every case-wide `UNRESOLVED` objection thread, client-side sorted longest-waiting-first by elapsed time since `raisedAt`; requires no new endpoint or schema change — reuses F02's existing `getUnresolvedObjections` with one additive `exhibitLabel` read-time join and the existing live-sync polling hook.
- **F22 — Multi-Case Support with Case Selector *(Phase 7.1)*:** An explicit, traceable reversal of the PRD's prior single-case-scope exclusion — replaces the hardcoded `DEMO_CASE_NUMBER` assumption with a header-level Case Selector and explicit `caseId` scoping threaded through every service function; requires no schema change, since every relevant table already carries a `caseId` foreign key.
- **F23 — Versioned Jury Packages with PDF Export *(Phase 7.1)*:** Replaces the `window.print()`-based export with real, server-generated PDF export (`@react-pdf/renderer`, the release's one new runtime dependency) and adds an immutable, sequentially-numbered version to every finalization, so a prior finalized package's exact contents remain independently retrievable and re-exportable rather than being overwritten by the next draft/finalize cycle.
